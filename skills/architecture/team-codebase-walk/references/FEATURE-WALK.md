# Feature 引导走读规则

## 目录

- 1. 触发条件
- 2. 主动提问原则
- 3. Feature 候选提取
- 4. 分层走读节奏
- 5. 用户反馈处理
- 6. 下一轮问题
- 7. 沉淀要求

## 1. 触发条件

满足任一条件时使用本规则：

- 用户说“带我理解代码库”“按功能讲”“从 feature 开始”“走读 onboarding 结果”。
- 用户没有指定明确模块或源码文件。
- 用户指定了 feature 名称、功能编号或功能域。
- 用户想知道某个功能怎么实现、怎么修改、怎么调试或有什么风险。

## 2. 主动提问原则

走读开始时不要直接展开全量功能。先用 1~3 个短问题收敛目标：

1. 你想先看哪个 feature？如果用户没有指定，从 `feature-inventory.md` 推荐 3~7 个选项。
2. 你这次的目标是理解、修改、调试、风险评估，还是建立整体阅读路径？
3. 你希望深度到哪里：概览、入口与调用链、数据/配置/接口、测试验证，还是修改影响面？

如果用户已经明确 feature 和目标，不要重复询问；直接进入走读，并在结尾主动给下一步选项。

## 3. Feature 候选提取

优先读取：

- `feature-inventory.md`：已完成详细设计的 feature。
- `feature-candidates.md`：候选 feature，只能标注为候选，不冒充完成层。
- `features/Fxxx-*/feature-overview.md`
- `features/Fxxx-*/detailed-design.md`
- `features/Fxxx-*/evidence.md`

推荐 feature 时按以下顺序排序：

1. 用户明确提到的功能编号、名称、模块或业务词。
2. `feature-inventory.md` 中置信度高、入口清楚、证据链完整的 feature。
3. 与用户目标相关的 feature，例如修改型优先有 change recipe 或测试证据的 feature。
4. 候选层 feature 放在最后，并明确“只适合初步探索”。

推荐格式：

| 选项 | Feature | 适合目标 | 入口 | 置信度 |
| --- | --- | --- | --- | --- |

## 4. 分层走读节奏

按用户反馈逐层推进，不要一次性讲完所有层。

### L0 设计灵魂与场景

每个 feature 走读必须先讲这一层。先让开发人员知道“为什么有它”，再看“代码怎么做”。

- 设计灵魂：这个 feature 的核心设计意图是什么，它在系统中承担什么角色。
- 场景：它在什么用户场景、业务流程、系统事件、接口调用或后台任务中被触发。
- 服务对象：用户、调用方、上游模块、下游模块或外部系统是谁。
- 问题边界：它解决什么问题，不解决什么问题。
- 成功信号：什么现象说明这个 feature 正常工作。
- 失败/异常场景：什么情况会暴露它的风险或边界。

如果 onboarding 文档没有明确设计意图，必须基于 feature overview、入口、调用方、测试和源码做推断，并标注“推断”或 `[TODO]`。

### L1 概览

- 这个 feature 解决什么问题。
- 调用方或用户是谁。
- 入口在哪里。
- 主要源码和文档证据。

### L2 入口与调用链

- 从入口到核心处理的路径。
- 关键函数、类、handler、service 或任务。
- 哪些分支和状态需要注意。

### L3 数据、配置、接口

- 请求/响应、消息、DTO、实体、schema 或协议模型。
- 配置键、环境变量和默认值。
- 外部服务、数据库、缓存、队列或文件系统依赖。

### L4 测试与验证

- 相关测试、fixture、mock、仿真器或样例。
- 可以运行或参考的验证命令。
- 未检测到测试证据时明确标注。

### L5 修改路径与风险

- 如果要改这个 feature，从哪里开始。
- 需要联动哪些文件、配置、测试或文档。
- 高风险点、历史 TODO/FIXME、高变更文件和不确定项。

## 5. 用户反馈处理

每轮结束时根据用户反馈决定下一步：

- 用户说“继续”：进入下一层。
- 用户说“太细”：回到概览，压缩解释。
- 用户说“源码”：打开对应源码路径做证据追踪。
- 用户说“我要改”：切到修改型，输出修改路径和验证建议。
- 用户说“哪里有风险”：切到风险型，读取 risk-notes、source-map 和相关源码。
- 用户切换 feature：记录切换原因，更新 `question-index.md`，开始新 session 或新 deep dive。

## 6. 下一轮问题

每轮输出末尾主动给 2~4 个下一步选项，例如：

- 继续看这个 feature 的入口调用链。
- 继续看数据模型和配置。
- 看它的测试与验证方式。
- 切到另一个相关 feature。
- 按“我要修改这个功能”的视角重新走一遍。

不要问开放到无法行动的问题，例如“你还想知道什么”。要给具体可选方向。

## 7. 沉淀要求

走读沉淀必须记录：

- 本轮主动提问。
- 用户选择或反馈。
- 选中的 feature 编号、名称、功能域和置信度。
- 设计灵魂和场景。
- 当前走读层级。
- 下一轮建议问题。

如果进入 L2 以上或跨多个源码文件，写入 `sessions/`。如果追踪跨模块调用链、修改影响面或调试路径，写入 `deep-dives/`。
