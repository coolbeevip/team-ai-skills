# 引导式代码库走读工作流

## 目录

- 1. 目标与边界
- 2. 阶段一：定位上下文
- 3. 阶段二：问题分类
- 4. 阶段三：Feature 清单提取与主动提问
- 5. 阶段四：知识底座阅读
- 6. 阶段五：源码证据追踪
- 7. 阶段六：引导式解释
- 8. 阶段七：沉淀记录
- 9. 证据不足处理
- 10. 最终回复

## 1. 目标与边界

本技能面向“已生成或正在使用代码库接手文档后的理解过程”。它不是重新生成全量接手文档，也不是直接实现代码变更。

默认只写：

```text
team-spec/active/{slug}/design/codebase-walk/
```

不得修改业务源码、测试、构建配置、部署配置、迁移脚本或 `codebase-onboarding/` 产物。

## 2. 阶段一：定位上下文

1. 确定目标仓库路径。
2. 确定唯一 slug 或明确的 onboarding 产物路径。
3. 定位默认输入：
   - `team-spec/active/{slug}/design/codebase-onboarding/`
4. 定位默认输出：
   - `team-spec/active/{slug}/design/codebase-walk/`
5. 记录用户当前关注点：
   - feature、模块、接口、数据流、配置、测试、风险、bug、修改目标或学习目标。

无法唯一确定 slug 或 onboarding 路径时才询问用户。若用户的问题足够具体但 onboarding 缺失，可以做最小源码阅读，并在结果中标注缺少知识底座。

## 3. 阶段二：问题分类

按主目标选择一种或多种类型：

| 类型 | 用户表达 | 主要产物 |
| --- | --- | --- |
| 理解型 | “这个模块是干什么的” | `sessions/` |
| 追踪型 | “这个请求/功能怎么走到这里” | `deep-dives/` |
| 修改型 | “我要改这个能力，从哪里下手” | `sessions/` 或 `deep-dives/` |
| 调试型 | “这个问题可能在哪里” | `deep-dives/` |
| 风险型 | “这里有什么坑/依赖/联动” | `sessions/` |
| 学习路径型 | “带我读这个项目/模块” | `sessions/` |

若用户问题宽泛，进入 feature 主动提问流程，不要一次性展开全仓库。

## 4. 阶段三：Feature 清单提取与主动提问

围绕 onboarding 生成的 features 做走读时，读取 `FEATURE-WALK.md`。

1. 读取 `feature-inventory.md` 和 `feature-candidates.md`。
2. 若用户未指定 feature，推荐 3~7 个 feature 选项，并主动问用户选择。
3. 同时询问用户本轮目标：理解、修改、调试、风险评估或学习路径。
4. 同时询问用户期望深度：概览、入口调用链、数据/配置/接口、测试验证或修改影响面。
5. 若用户已指定 feature 和目标，不重复询问，直接进入对应层级。

主动提问必须具体、短、可选择。不要问“你想了解什么”这类泛问题。

## 5. 阶段四：知识底座阅读

优先读取 onboarding 产物，而不是直接从零扫仓库：

1. `index.md`：确认文档地图。
2. `project-overview.md`：确认项目意图和源码现实。
3. `architecture-overview.md`：确认系统边界、入口和核心流转。
4. `feature-inventory.md` / `feature-candidates.md`：确认功能完成层和候选层。
5. `modules/module-map.md` / `modules/dependency-map.md`：确认模块职责和依赖。
6. `ai-onboarding/reading-path.md`：获取建议阅读顺序。
7. `ai-onboarding/change-recipes.md`：获取常见修改路径。
8. `ai-onboarding/risk-notes.md`：获取风险提示。
9. `traceability/source-map.md`：定位源码证据。
10. `traceability/open-questions.md`：识别待确认项。
11. `scan-summary.json`：获取机器扫描候选和风险信号。

只读取与当前问题相关的文档，不要把全部文档塞进上下文。

## 6. 阶段五：源码证据追踪

围绕当前问题回到源码补强：

- 从 onboarding 指向的源码路径开始。
- 优先读入口、公开接口、核心服务、关键数据模型、配置加载、测试和调用方。
- 对追踪型问题，建立“入口 -> 中间处理 -> 数据/状态变化 -> 外部依赖 -> 返回/副作用”的链路。
- 对修改型问题，建立“需要改哪里 -> 联动文件 -> 验证命令 -> 风险”的路径。
- 对调试型问题，建立“现象 -> 可能分支 -> 日志/配置/状态 -> 验证点”的路径。

每个关键结论必须标注：

- onboarding 文档结论。
- 源码显式证据。
- 代码推断。
- `[TODO]` 证据不足。
- `[ASK USER]` 需要用户业务判断。

## 7. 阶段六：引导式解释

面向开发人员输出时使用以下顺序：

1. 先讲设计灵魂和场景：为什么有这个 feature、服务谁、在什么场景触发、解决什么问题、边界在哪里。
2. 再给 3~8 行结论。
3. 明确本轮选中的 feature、用户目标和走读层级。
4. 给建议阅读路径，按文件顺序说明为什么读。
5. 解释核心实现链路，避免只列文件。
6. 标注关键源码、配置、测试和文档证据。
7. 指出容易误解的命名、历史文档、生成代码、隐式约定和风险。
8. 主动给出 2~4 个下一步选项，让用户选择继续看调用链、数据/配置、测试验证、修改影响面或切换 feature。

不要把回答写成泛泛教程。必须围绕用户当前关注点。

## 8. 阶段七：沉淀记录

写文档前读取 `OUTPUT-SPEC.md`。

默认：

- 每次跨文件走读写入 `sessions/{yyyy-mm-dd}-{topic}.md`。
- 深入专题分析写入 `deep-dives/{topic}.md`。
- 更新或创建 `question-index.md`，记录问题、状态、选中的 feature、用户反馈、产物路径和后续问题。

若用户只要即时口头解释，可以不写文件；但最终回复要说明未沉淀文档。

## 9. 证据不足处理

按以下顺序处理：

1. 检查 onboarding 产物是否已有相关结论。
2. 根据 source-map、module-map、feature-inventory 回到源码。
3. 若源码证据仍不足，写“推断”并说明推断依据。
4. 若推断不稳妥，写 `[TODO]`。
5. 若需要业务规则、外部系统或团队约定，写 `[ASK USER]`。

不要为了完整感编造调用链、接口契约或配置规则。

## 10. 最终回复

最终回复使用中文，并包含：

- 本次走读主题和结论。
- 设计灵魂和场景。
- 主动提问、用户选择和当前 feature。
- 建议阅读路径。
- 已写入或建议写入的产物路径。
- 关键来源文件。
- 待确认项和下一轮可选问题。
