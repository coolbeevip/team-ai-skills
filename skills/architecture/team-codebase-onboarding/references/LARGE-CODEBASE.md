## 目录

- 1. 触发条件
- 2. 分阶段模式
- 3. 功能域划分

- 5. 生成代码处理
- 6. Monorepo 处理
- 7. 大型仓库输出策略

## 1. 触发条件

满足以下任一条件时，默认采用分阶段模式：

- 源码文件数量超过 1000。
- 仓库存在明显生成代码目录、协议模型目录或大规模命名同构文件。
- 顶层存在多个业务域、控制面/用户面、仿真器、适配层或大量测试工程。
- 存在 monorepo/workspace，例如多 package、多 app、多 service。
- 构建入口不完整，无法可靠推断全量可执行产物。

大型仓库中，不要逐文件详读所有叶子工具文件。先建立顶层索引，再按模块深入。

## 2. 分阶段模式

分阶段模式产物分两层：

- 候选层：`feature-candidates.md` 或 `docs/FILE_INDEX.md` 中的候选功能、候选模块、候选入口。候选项只表示“值得展开”，不表示已完成详细设计。
- 完成层：`feature-inventory.md` 或正式模块/API/数据文档中已完成证据链闭环的内容。

候选功能进入正式功能清单前，必须满足：

- 已确定功能名称、功能域、入口和主要源码路径。
- 已明确本轮会生成对应功能文档或模块文档。
- 至少有一个源码、配置、测试或文档证据。

## 3. 功能域划分

大型 C/C++、嵌入式、通信系统、协议栈项目中，功能域优先按业务/系统边界划分，而不是按语言目录或技术分层划分。

常见功能域：

- CP：控制面、信令、配置、连接管理、切换、会话、接入控制。
- UP：用户面、数据转发、承载、加解密、头处理、队列、性能路径。
- OAM：配置管理、性能统计、告警、日志、运维代理。
- Interface：跨模块接口、协议适配、异步响应、消息编解码边界。
- Emulator/Test：仿真器、Fake/Mock、集成测试场景，用于反推真实功能流程。
- Protocol Model：协议结构、ASN.1/IDL/protobuf 生成模型，只作为协议证据和数据结构证据。

不要把 `controller`、`service`、`repository`、`src`、`include`、`export` 这类技术分层直接当作功能。

## 4. 入口识别优先级

通信系统和 C/C++ 仓库的入口识别优先级：

1. 应用启动、控制类、主循环、线程入口、消息服务、任务调度器。
2. 接口层和适配层，例如 `*Interface`、`*Api`、`*Proxy`、`*Adapter`、`*Control`。
3. 协议过程、消息处理、状态机、事件处理、回调函数。
4. 集成测试和场景测试，例如 `*TestCase`、`ut_*`、`emulators/`、`Fake*`、`Mock*`。
5. 协议模型和生成代码，仅用于补充消息、IE、PDU、字段和流程证据。

对大型仓库，测试和仿真器经常是最清晰的功能反推入口。测试名、fixture、Fake/Mock 类型可以作为候选功能证据，但不能替代生产代码证据。

## 5. 生成代码处理

对生成代码只做结构采样和证据引用，不默认逐文件阅读。

生成代码包括：

- 协议编解码产物。
- ASN.1/IDL/protobuf 生成文件。
- 超大规模命名同构文件。
- 构建过程生成的聚合源文件。
- 二进制或中间产物：`*.o`、`*.a`、`*.so`、`*.dylib`、`*.dll`、`*.d`、`*.gcda`、`*.gcno`、`*.profraw`。

生成代码不能直接作为功能入口，除非仓库证据表明它承载手写业务逻辑。

对于命名同构且规模巨大的生成代码目录，例如大量 `AL_*` 协议文件，应汇总：

- 协议族或消息族名称。
- 目录和文件模式。
- 文件规模。
- 生成特征。
- 被手写业务代码引用的位置。
- 与功能或模块的映射关系。

## 6. Monorepo 处理

若仓库存在 workspace/monorepo 迹象，分别识别每个 package/app/service：

- 名称和路径。
- 技术栈和依赖清单。
- 构建、测试、启动命令。
- 对外接口。
- 与其他 package/app/service 的依赖关系。
- 是否为库、应用、服务、工具、测试夹具或示例。

根级文档先给全局关系，再按子项目展开。

## 7. 大型仓库输出策略

大型仓库输出时采用“高层结论 -> 模块表 -> 关键文件追踪”的顺序：

1. 高层结论：语言、类型、规模、主要子系统、核心入口、未知项。
2. 模块表：模块、路径、职责、入口、关键依赖、风险点、置信度。
3. 关键文件追踪：只列对理解、构建、运行、修改有价值的关键文件。
4. 功能候选池：列出待展开功能和需要人工确认的问题。
5. 批次建议：指出下一批最值得深入生成详细设计的功能。

不要把全量文件列表复制进正文。全量或半结构化索引应放在 JSON 摘要或文件索引文档中，并做规模控制。
