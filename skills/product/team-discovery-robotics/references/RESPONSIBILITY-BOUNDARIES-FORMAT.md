# 机器人系统责任边界与接口合同

在范围冻结、系统架构、Solution Specification 和 Software Specification 中使用此合同。先按运行时职责划分系统，再映射到本体、算法、AI、平台或供应商团队；组织可以合并多个层级，但不得省略层间接口、安全权限和唯一负责方。

## 1. 分层原则

- `层级` 表示运行时责任、控制权限和失效边界，不等于固定组织架构。
- `团队` 是交付责任映射；一个团队可以负责多层，多个供应商也可以共同实现一层。
- 每项关键能力必须有且只有一个 `Accountable` 角色；多个团队可以共同 `Responsible`。
- 越接近实时控制、物理安全和本体耦合的能力，越靠近下层；越接近业务语义、长程目标和跨技能组合的能力，越靠近上层。
- 安全约束可以由多层共同设计，但最终限幅、拒绝和停机权必须在机器人平台层独立生效。

## 2. 三层运行时责任模型

| 层级 | 主要责任 | 典型交付 | 明确不负责 |
| --- | --- | --- | --- |
| L1 机器人平台与本体（Robot Platform & Embodiment） | 本体硬件、固件、驱动/HAL、标定、实时控制、关节/底盘控制器、运动学与动力学约束、轨迹执行、设备健康和安全限幅 | 稳定的 Capability/Motion API、设备状态、故障码、安全状态和硬件验证证据 | 不嵌入“补货、收拾房间”等业务任务语义，不执行长程任务决策 |
| L2 机器人自主与技能（Robot Autonomy & Skills） | 感知、定位、空间/语义世界模型、全局与局部导航规划、操作与抓取规划、VLA/学习策略、技能状态机、结果验证和局部恢复 | 可复用 Skill API、技能包、场景适配参数、技能级指标与回放证据 | 不直接解释业务订单并自由拆解长程任务，不绕过平台安全和控制约束 |
| L3 任务智能与 Agent（Task Intelligence & Agent） | 意图理解、任务分解、技能选择与调度、长程规划、任务上下文/记忆、业务规则、外部系统协同和人工确认 | 任务计划、Skill 调用、业务状态、任务级解释与审计记录 | 不直接发送电机、关节、速度或轨迹命令，不绕过技能前置条件与安全确认 |

实际组织映射使用真实团队名称，例如本体团队、算法工程师团队、AI 团队或外部供应商。若同一团队跨层负责，仍保留逻辑接口、独立测试和故障隔离。

## 3. 规划、VLA 与安全归属

| 能力 | 主责层 | 边界说明 |
| --- | --- | --- |
| 任务/目标/步骤规划 | L3 | 决定做什么、先后顺序和调用哪个 Skill，不产生运动控制命令 |
| 全局/局部路径规划与动态避障 | L2 | 依据地图、代价、约束和环境状态生成或重规划可执行路径 |
| 抓取、操作与机械臂运动规划 | L2 | 生成满足碰撞、可达性和任务约束的候选轨迹或策略 |
| 轨迹跟踪、伺服控制与最终限幅 | L1 | 执行轨迹，实施频率、速度、力矩、工作空间和安全限制 |
| 直接输出机器人动作的 VLA/策略 | L2 | 与本体动作空间、控制频率、训练数据和安全回退强耦合，必须通过 L1 接口执行 |
| 高层具身推理、VLM 或 Agent 规划 | L3 | 输出任务目标、步骤或 Skill 调用；不得把自然语言结果直接转换为未校验控制命令 |
| 安全策略设计与风险分析 | 跨层 | L2/L3 可以请求停机或施加保守策略，L1 保留不可绕过的拒绝、限幅和停机权 |

本体供应商可能把通用导航栈作为平台能力交付，但场景化规划责任仍要按其输入、输出、可配置范围、验证责任和故障处理归属明确记录，不能仅凭组件随本体提供就默认属于 L1。

## 4. 调用方向与禁止路径

```text
业务系统/用户
      ↓ 任务目标与约束
L3 Task Intelligence & Agent
      ↓ Skill API
L2 Robot Autonomy & Skills
      ↓ Capability/Motion API
L1 Robot Platform & Embodiment
      ↓ 已校验控制
控制器与硬件

状态、进度、结果证据和故障逐层向上反馈；安全事件可以抢占任意层。
```

禁止以下路径：

- L3 直接调用关节、电机、底盘速度、轨迹或安全控制器。
- L2 绕过 L1 的限幅、资源仲裁、急停、保护停或故障状态。
- L1 根据业务语义自行决定订单、任务优先级或长程工作流。
- 任一层用未版本化的隐式共享状态替代正式接口。
- Agent 或生成式模型把自由文本作为可直接执行的控制消息。

## 5. 跨层能力分工

| 横切能力 | L1 | L2 | L3 |
| --- | --- | --- | --- |
| 状态与世界模型 | 原始设备状态、坐标系、时间同步 | 空间、对象、可达性和语义状态 | 任务上下文、业务状态和长程记忆 |
| 安全 | 急停、保护停、限幅、看门狗、故障安全 | 碰撞检查、风险区域、技能前置条件和恢复 | 高风险任务确认、权限、业务禁令和人工升级 |
| 可观测性 | 硬件遥测、控制周期和故障码 | 技能轨迹、阶段指标和结果证据 | 任务链路、决策理由和业务审计 |
| 配置与版本 | 固件、驱动、标定和控制参数 | 地图、模型、技能与场景参数 | 策略、提示、业务规则和流程版本 |
| 数据与 MLOps | 传感器采集质量和时间基准 | 数据集、训练、评测、模型发布和漂移 | 任务反馈、人工标注触发和业务效果 |
| 安全与权限 | 设备身份、可信启动和控制通道 | 技能权限、模型供应链和数据访问 | 用户/租户权限、工具授权和提示注入防护 |

数据平台、MLOps、安全、DevOps 和验证团队可以作为横向团队，不必强行成为第四个运行时层。

## 6. 系统责任与 RACI

先填运行时层级，再填真实组织。`A` 只能有一个；供应商交付不自动等于客户方验收责任。

| REQ/能力/组件 | 运行时层级 | Accountable（A） | Responsible（R） | Consulted（C） | Informed（I） | 交付与验收证据 | 上下游接口 |
| --- | --- | --- | --- | --- | --- | --- | --- |
|  | L1 / L2 / L3 / 跨层 |  |  |  |  |  |  |

对安全关键、跨团队或外部供应商能力，再补充：设计批准人、集成人、验证人、现场放行人、运行维护人和故障升级路径。避免同一个人在没有独立复核时同时承担安全设计与最终放行。

## 7. Skill API 合同

| 字段 | 必须定义的内容 |
| --- | --- |
| 身份与版本 | Skill ID、语义版本、Owner、兼容范围 |
| 目的与参数 | 业务无关的能力描述、输入 Schema、单位、坐标系和约束 |
| 前置条件 | 本体状态、资源、环境、权限、安全和数据新鲜度 |
| 生命周期 | start、progress、pause、resume、cancel、timeout 和终态 |
| 结果与证据 | 成功条件、结构化结果、置信度、观测证据和副作用 |
| 失败语义 | 稳定错误码、可重试性、最大重试、降级和人工介入 |
| 并发与资源 | 底盘、机械臂、传感器等资源锁，优先级、抢占和幂等 |
| 安全 | 风险等级、必要确认、禁止条件、停止行为和 L1 约束依赖 |

## 8. Capability/Motion API 合同

| 字段 | 必须定义的内容 |
| --- | --- |
| 身份与能力 | primitive ID、版本、Owner、支持的本体/配置 |
| 输入 | 命令类型、坐标系、单位、范围、轨迹或目标约束 |
| 时序 | 控制频率、截止时间、最大延迟、时间戳和同步要求 |
| 状态反馈 | 执行状态、位置/速度/力、质量标志和故障码 |
| 安全边界 | 速度、力矩、工作空间、碰撞、限位和权限约束 |
| 生命周期 | accept/reject、start、cancel、controlled stop、protective stop、emergency stop |
| 资源仲裁 | 控制权、租约、互斥、抢占和冲突处理 |
| 验证 | 仿真、台架、硬件在环和本体实测的通过门槛 |

## 9. 边界判定与评审门槛

能力归属不清时依次判断：它是否必须在安全停机或断网时继续工作；是否依赖确定性时序；是否与具体本体动作空间和标定强耦合；是否能跨本体复用；是否包含业务语义或长程目标。前三项越强越靠近 L1/L2，后两项越强越靠近 L2/L3。

进入系统方案阶段前必须确认：

- 每项关键需求已有运行时层级、真实团队/供应商映射和唯一 Accountable。
- L3 → L2 → L1 的调用方向、反馈路径、取消、超时和安全抢占已经定义。
- Skill API 与 Capability/Motion API 的 Owner、版本和最小合同已经明确，或被列为有负责人和期限的阻塞项。
- 规划、VLA、安全、世界模型和可观测性没有重复拥有或无人负责。
- 未解决的安全权限、直接控制越权或关键接口责任空洞，必须阻塞 Gate-6；一般组织名称或人员未定可作为非阻塞遗留项。
