# VLA 在线检索与选型格式

当场景可能使用 Vision-Language-Action（VLA）、机器人基础模型或具身推理模型时使用本格式。模型生态变化快，文件中的任何名称只能作为检索种子，不能作为最新性证据。

## 1. 在线检索合同

在写出推荐模型、版本或技术栈前必须实时联网检索，不能只依赖记忆、训练语料或既有文档：

1. 先做生态检索，寻找截至检索日仍活跃的新模型、重大版本、官方替代路线和停止维护项目；不要只搜索已经熟悉的模型名称。
2. 再逐个访问官方项目页、论文、模型卡、代码仓库、发行说明、SDK 文档、许可和硬件指南进行核实。二手文章只能用于发现线索，不能单独支撑推荐。
3. 记录检索日期、查询主题、官方链接、版本或 commit/tag、发布状态、最近更新日期和事实摘要。区分 GA、Early Access、Preview、Trusted Tester、研究发布和已停止维护。
4. 核对代码、权重、训练或微调能力、许可、商业使用、地区与账号限制、数据条款、支持本体、依赖版本、所需算力和官方已知限制。不要把“论文公开”误写成“模型可获得”。
5. 如果无法联网或官方资料无法访问，可以继续定义需求和 PoC，但不得声称技术方案是最新或已完成选型；把在线检索列为阶段 6 阻塞项。

## 2. VLA 必要性门槛

先说明为什么任务需要 VLA，不要因为用户提到“智能”就默认选择 VLA。至少比较：

- 一个模块化非 VLA 基线，例如确定性感知、任务规划、运动规划和控制组合；
- 一个与场景匹配的传统学习策略，例如行为克隆、ACT、Diffusion Policy 或专用策略；
- 多个合格 VLA 候选。

只有当开放词汇指令、跨对象或跨任务泛化、语言条件控制、长尾适应或数据复用带来的价值足以覆盖数据、算力、时延、验证和安全成本时，才推荐 VLA。区分直接输出机器人动作的 VLA、只做空间理解或高层编排的 VLM/Embodied Reasoning 模型，以及生成训练数据的世界模型；不得混为同一类方案。

## 3. 候选集要求

存在足够合格选项时至少保留三个 VLA 候选，覆盖与当前场景相关的不同路线，例如开放权重可自部署、轻量端侧、厂商平台或受限商业服务。候选不足三个时，列出检索到但被排除的方案及排除证据，不能静默退化为单一模型。

OpenVLA/OFT、SmolVLA/LeRobot、openpi、Isaac GR00T、Gemini Robotics 等名称只能作为起始检索词。每次执行都必须搜索后来发布的模型和版本，并用检索日的一手资料重新判断；不得因为本格式出现某个名称就默认推荐它。

先按不可妥协条件筛选：指定本体与动作空间、控制频率、相机和状态输入、部署网络、算力与功耗、安全隔离、数据合规、许可、预算及可获得性。不满足硬条件的模型进入排除表，不参与加权打分。

## 4. 场景化比较矩阵

| 维度 | 必须核对的内容 |
| --- | --- |
| 身份与成熟度 | 模型、准确版本、发布日期、GA/EA/Preview/研究状态、维护活跃度 |
| 开放与许可 | 代码、权重、训练配方、数据、商业许可、API/账号/地区限制 |
| 本体适配 | 已验证本体、单/双臂或移动操作、关节与末端动作空间、适配器和标定需求 |
| 输入与输出 | 相机数量和视角、语言、机器人状态、动作表示、action chunk、频率和时域 |
| 数据与训练 | 预训练数据范围、任务演示量、数据格式、微调方式、训练算力和训练周期 |
| 部署资源 | 参数规模、GPU/NPU、显存/内存、端侧或服务端、网络依赖、功耗和成本 |
| 实时与可靠性 | 推理延迟、控制频率、异步推理、抖动、断网、恢复、确定性回退和人工接管 |
| 能力证据 | 与本场景相近的任务、对象、环境和本体；同协议 benchmark 或现场 PoC |
| 工程生态 | SDK、ROS/中间件集成、仿真、数据采集、调试、评测、部署和版本兼容 |
| 风险 | 幻觉或错误动作、域偏移、长时任务漂移、安全隔离、供应商锁定和维护风险 |

优缺点必须写成相对当前场景和本体的因果判断，例如“模型较小”只有在它确实满足本体算力和控制周期时才算优势。不同论文、数据集、本体或评测协议的分数不得直接排序；厂商自测与独立复现必须分栏记录。

## 6. 同条件 PoC

让进入终选的候选使用同一机器人配置、相机与状态输入、任务指令、训练/微调数据预算、测试场景、随机种子策略和安全外壳进行比较。至少测量任务成功率、子步骤成功率、动作频率、端到端延迟、恢复能力、人工介入、安全违规、算力与功耗。预先定义通过门槛和失败后的非 VLA 回退；不得用演示视频或单次成功代替 PoC。
