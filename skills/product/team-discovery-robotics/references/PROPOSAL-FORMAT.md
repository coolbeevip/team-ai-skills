# 机器人项目方案书格式

在 `spec/discovery.md`、`design/solution-specification.md` 和 `design/software-specification.md` 完成、关键事项全部确认并通过一致性检查后，使用此格式生成 `team-spec/active/{slug}/design/proposal.md` 正式终稿。方案书面向客户、产品负责人、技术负责人和项目决策者，只呈现最终方案与约定，不解释探索、分析、推导、检索、比较或文档形成过程。

## 目录

1. 终稿生成前内部检查
2. 方案书模板
3. 方案书质量检查

## 1. 终稿生成前内部检查

- 本节仅供技能执行时检查，不得写入最终 `proposal.md`。
- 先完成并一致性检查 Discovery、Solution Specification 和 Software Specification，再生成方案书终稿。
- 只提炼已确认事实、最终决策和正式约定，不从营销语言或常识补造能力、价格、工期、ROI 或客户承诺。
- 用客户和决策者可理解的语言说明价值与方案；详细参数、接口和测试用例引用技术附件，不展示公式草稿、模型筛选或分析记录。
- 所有硬件型号、软件版本、价格、供货、许可和技术状态保留事实截止日期与来源。
- 存在源文档冲突、安全阻塞、本体硬冲突、待确认关键事项或关键选型证据缺失时，不得生成方案书，返回对应阶段修订。
- 方案书不得反向修改已经确认的需求或规格；发现冲突时先回到对应源文档修订并重新确认。

生成前检查：

| 检查项 | 结果 | 证据/差异 | 处置 |
| --- | --- | --- | --- |
| Discovery 范围、Use Case、状态机、MVP 与验收基线完整 | 通过 / 未通过 |  |  |
| Solution Specification 系统与硬件配置、BOM、性能和责任边界完整 | 通过 / 未通过 |  |  |
| Software Specification 软件、算法、接口、部署和测试完整 | 通过 / 未通过 |  |  |
| 需求、决策、型号、版本、接口和指标在三份文档中一致 | 通过 / 未通过 |  |  |
| 阻塞与待确认关键事项已经全部关闭 | 通过 / 未通过 |  |  |

## 3. 方案书质量检查

- 执行摘要是否能独立回答为什么做、做什么、如何落地、投入、周期、价值和主要风险？
- 是否没有把合同指标、厂商参数、设计值和 PoC 实测混写为同一种承诺？
- 推荐软硬件、型号、版本、数量、接口和责任是否与详细规格一致？
- 是否只呈现最终推荐方案，没有候选比较、淘汰理由或内部决策过程？
- 是否同时说明 MVP 内、MVP 外、人工协作、异常、降级和安全边界？
- 预算、工期、ROI 和供货是否有口径、日期、来源与不包含项？
- 是否所有关键阻塞、待确认和专业复核事项均已关闭，不需要在终稿中解释处理过程？
- 是否引用详细规格而不是复制大量技术表格，且链接路径可用？
- 是否完全删除访谈记录、问题清单、候选比较、推导草稿、检索日志、内部检查、变更过程和文档形成说明？
- 是否不存在 `待确认`、`条件化草案`、未关闭阻塞或未决关键选项？
- 是否没有把厂商声明或计划中的 PoC 写成已经验证的承诺？
