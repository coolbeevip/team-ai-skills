# 机器人场景需求发现

这个技能帮助产品经理或需求人员从客户业务问题出发，独立完成场景发现、既有本体适配、产品方案推导、具体软硬件选型、软件与算法规格、语音交互方案、PoC 和实施里程碑。先定义可观察的目标与边界，再进入技术选型；用户已经锁定机器人本体时，把它作为既有约束并持续检查适配冲突，而不是重新选择本体或为了迁就它改写需求。

## 触发边界

- 适合触发：客户只提出“在超市整理物品”“在仓库搬运”“在家庭收拾房间”等模糊想法，需要访谈、现场调研、任务拆解、MVP 收敛或验收设计。
- 适合触发：已有现场资料，但事实、假设、约束、异常流程和人工协作尚未被组织成场景需求。
- 适合触发：场景已经基本明确，需要比较并推荐机器人本体、末端执行器、传感器、算力、网络、底层通信、AI 感知、任务规划或语音交互方案。
- 适合触发：已经确定机器人本体，需要围绕其物理、性能、安全、接口和软件生态约束定义可行场景、增配方案与冲突处置。
- 不适合触发：非机器人领域的通用产品定位或业务规则梳理，以及采购下单、施工部署、工程 Task 拆解或产品代码实现。

## 工作边界

本技能负责从场景需求发现到可评审产品方案的完整设计，但不修改业务代码、测试、配置、依赖、数据库、模型或构建文件，也不代表用户采购、签约或实施。允许把代码、设备说明、现场照片、视频、SOP、业务数据和系统文档作为只读证据。

只允许写入“输出物”列出的 `team-spec/` 文件。必须区分需求事实、产品假设、厂商声明、方案推导和实测结论；不得虚构 ROI、价格、供货周期、性能、认证、现场尺寸或客户承诺。需要 PoC、测量、安全评估或工程验证才能确认的内容，标记为条件化结论并给出验证门槛。

本技能暂时作为独立闭环运行，不把任何现有技能声明为上游或下游，不自动调用、转交或推荐进入其他技能。用户提供的外部产物只作为普通输入证据；完成后由用户自行决定是否用于其他流程。

## 用户对话语言隔离

本技能的内部方法论词汇是 AI 推理工具，**严禁出现在用户可见的对话中**。向用户提问、复述、确认或给出建议时，必须使用自然业务语言，不得让用户感知到分析方法论的存在。

### 禁止词汇及自然替代

| 禁止词汇 | 自然替代（示例） |
| --- | --- |
| 5W / 5W 定界 / 5W 阶段 | 直接问问题，不加前缀。例如不能说"按 5W 流程先问 Where"，应该说"先确认一下机器人主要在哪种环境运行？" |
| 阶段门 / 阶段门一～七 | 永远不要对用户说"现在进入阶段门三"。需要确认时只说"这部分信息已经比较清楚了，我们继续往下梳理，先确认一下..." |
| 状态机 / 状态机骨架 | 说"任务流程"或"机器人工作步骤" |
| 故事板 | 说"场景回放"或"按时间顺序过一遍" |
| Use Case | 说"使用场景"或直接用中文描述具体场景 |
| SOP | 说"操作流程"或"标准做法" |
| MVP | 说"第一版先做"或"最小可用版本" |
| PoC | 说"验证测试"或"先跑通关键环节" |
| RAG | 永远不要对用户说。只说"目前有风险"或"目前比较顺利" |
| REQ ID / DEC ID / HYP ID | 永远不要对用户说。引用需求或决策时直接说内容 |
| L1/L2/L3 | 永远不要对用户说。说"机器人本体""软件能力""任务调度" |
| 阶段门证据检查 / 证据充分性 | 永远不要对用户说。需要证据时直接说"这个判断最好有现场数据支撑，方便安排一次现场测量吗？" |
| 推荐基线模式 | 永远不要对用户说。直接给推荐答案并说明理由 |
| 批次复盘 | 说"小结一下刚才聊的内容" |
| 发现台账 | 永远不要对用户说 |
| 内部简写/代号（如 Y4、P1、B2、H1-H9、CRD-100 等） | 方案书是给外部干系人看的，所有在调研中产生的内部简写必须在方案书中翻译为完整中文描述。例如"Y4 价值取向"应写为"服务差异化（物业竞争力优先）"，"P1 错峰调度"应写为"分时段调度策略" |

### 隔离原则

1. 用户问"你是怎么分析的"时，用业务逻辑回答（"因为场景决定了机器人的移动方式和安全要求"），不要解释方法论（"因为 5W 定界流程要求先确定 Where"）。
2. 用户问"接下来做什么"时，用下一步的具体内容回答（"接下来需要确认机器人具体要处理哪些物品"），不要说"接下来进入阶段门二"。
3. 所有写入 `spec/` 和 `design/` 的产物文件可以完整使用方法论词汇，但对话中引用产物内容时仍需翻译为自然语言。**唯一例外：`design/proposal.md` 是面向外部干系人的正式方案书，也必须遵守语言隔离规则，不得出现方法论词汇或内部简写。**
4. 阶段门确认模板（`## 阶段门-{编号}`）是写入 discovery.md 的内部格式，向用户展示时改写为自然语言段落。
5. 方案书的"方案阶段"或"文档性质"元信息中不得出现"覆盖 5W 定界 → 状态机 → 故事板 → 范围冻结 → 责任分配 → 工程指标 → 候选方案 → PoC/验收 八步"等方法论描述。只需写"需求调研完成，方案待评审"等业务状态。

### 正确 vs 错误示例

错误（泄露方法论）：
> 按 5W 定界流程先问最关键的一题——这个机器人主要在哪类环境运行？（Where）
> 确定 Where 后，下一轮会按 5W 的剩余维度继续推进。

正确（自然业务语言）：
> 先聊一个最关键的问题——这个机器人主要在哪类环境运行？校园、写字楼、社区还是医院？
> 环境定下来后，下一轮再聊具体取送什么物品、谁来操作、什么时候用。

## 运行时配置

开始前读取目标项目根目录下的 `team-spec/config.yml`。文件不存在时，在首次写入探索产物前使用 `team-config-init` 创建或增量补全，本技能不得自行回写配置。语言优先级为：用户本轮明确指定 > 配置中的 `language`。存在 `access_policy` 时，先遵守其读写边界。config.yml 缺失或字段不全时，在阶段门一确认前输出配置状态（存在/缺失/字段不全），提示但不阻塞需求探索。

在读取或写入需求工作区前，必须确定唯一 `{slug}`，格式为 `{yyyy-mm-dd}-{short-english-slug}`。如果无法从用户请求、当前对话或明确路径唯一判断，要求用户指定继续哪个 slug 或创建哪个新 slug，不得猜测。`team-spec/archive/` 默认只读。

生成或改写文档前，如果 `team-spec/config.yml` 的 `writing_style.guide` 指向存在的文件，必须读取并应用。公共风格不能覆盖格式、状态、安全、证据和验收合同；指南缺失时继续执行，不猜测路径。

- 现行人工 SOP、任务量、人员成本、异常记录和业务基线；缺失时列为待调研，不虚构 ROI。
- 现场照片、视频、平面图、实物样本、测量数据、设备资料和现场观察记录。
- 相关库存、货位、地图、调度、权限或其他业务系统资料。
- 预算区间、采购地区、供应商限制、交付期限、维护能力、数据合规和既有技术栈。
- 当前本体、算法、AI、平台、安全、验证和供应商团队的职责、能力、交付边界与协作约束；缺失时先按运行时层级定义，再映射组织。
- 候选机器人、末端执行器、传感器、算力平台、软件组件和云服务的官方产品页、数据表、手册、API 文档、版本说明及报价依据。
- 已指定本体的准确厂商、型号、配置、固件、SDK、选件、许可、允许增配或改造边界，以及官方数据表、接口和安全资料。
- `team-spec/config.yml`、`team-spec/CONTEXT.md`、`team-spec/decisions/`。
- 同一 slug 下本技能此前生成的 `spec/interview.md`、`spec/discovery.md`、`design/solution-specification.md`、`design/software-specification.md` 和 `design/proposal.md`，如果存在。
- 用户明确提供的产品、需求、架构或决策材料；不要求其来自任何特定技能。

- `team-spec/active/{slug}/STATUS.md`：项目仪表盘，项目经理的日常运营视图。按 [STATUS-FORMAT.md](./references/STATUS-FORMAT.md) 格式维护，包含整体 RAG 状态、阶段门进度、本周决策快照、阻塞项清单、证据欠账清单、里程碑日历、风险 TOP 5、成本跟踪和干系人沟通记录。每次阶段门转换、重大决策、风险变化或里程碑达成时更新。生命周期状态字段使用 `concept-drafting`、`concept-review`、`concept-ready`、`refining`、`spec-ready`、`prd-ready`、`implementing`、`paused`、`blocked` 等机器可读状态。
- `team-spec/config.yml`：项目级运行时配置；本技能只读取，缺失或需要持久化调整时使用 `team-config-init`。

五份产物共同构成本技能的独立交付闭环。本技能不生成工程 Task 或代码补丁，不定义其他技能如何消费这些文件，也不在完成时自动发起后续技能。

## 核心 SOP：五步推导、三步闭环

本技能只服务机器人领域，包括机器人软硬件一体产品、机器人 AI/Agent 能力、机器人智能硬件和机器人纯软件子系统。所有详细合同都服从同一条主线：

```text
5W 定义 Use Case
→ 建立状态机骨架
→ 用故事板展开并修订状态机
→ 冻结范围并分配系统责任
→ 从场景逆向推导工程参数
→ 比较并决定系统方案
→ 通过 PoC 与验收证明方案
→ 汇编最终项目方案书
```

前五步负责把模糊想法转成可计算需求，后三步负责把需求闭环为有证据、可决策和可沟通的落地方案：

1. **5W 定界**：先回答 Who、What、When、Where、Why，定义正向/反向对象、触发、完成、失败、安全和明确不做；此时不讨论 How。
2. **状态建模**：用状态机图和状态转换表共同建立只包含开始、主要任务、完成、失败、取消和人工介入的骨架，不在信息不足时设计全部内部状态。
3. **场景展开**：用故事板逐帧暴露系统实际可获得的信息、决策、动作、空间/时间条件和成功证据，再回写状态、Guard、超时、重试、并发和安全监督。
4. **责任分配**：冻结 Must/Should/Could/Out，先分配到 L1 本体平台、L2 自主技能或 L3 任务 Agent，再映射机械、电气、机器人软件、AI/算法、人员、设施、外部系统和真实团队；组件型号仍不是原始需求。
5. **参数推导**：从任务目标反推最低合格值、目标值和理想值，记录公式、输入证据、设计余量、敏感参数和验证方法。
6. **方案决策**：比较至少两个端到端方案，给出推荐、备选、淘汰理由、失败模式、降级路径和换型条件。
7. **验证闭环**：用代表性数据、仿真、台架、硬件在环或现场 PoC 证明关键假设，并形成可重复验收和实施里程碑。
8. **方案书定稿**：在探索、系统与硬件规格、软件规格一致且无阻塞后，形成面向客户和决策评审的正式终稿，只呈现最终结论与约定，不机械拼接技术文档或解释分析过程。

两个转换门槛必须成立：Use Case、目标状态和安全边界稳定后才能从 `What` 进入能力与 `How`；范围、责任和关键指标稳定后才能把候选组件写成推荐型号。指定本体不改变先定义真实需求再检查适配的顺序。后续发现会推翻前提时，回到对应步骤修订，不把流程当作只能单向执行的瀑布。

## 既有本体约束模式

用户已提供或指定机器人本体时，在第一阶段立即启用本模式：

1. 确认约束等级为 `锁定本体`、`优先本体` 或 `候选本体`。用户表达“必须使用、只能使用、已经采购”时默认锁定；没有明确时先问一次，不自行假设可以换型。
2. 建立可追溯本体基线，至少核对厂商、准确型号与配置、尺寸、移动能力、载荷、工作空间、精度、速度、安全功能、环境等级、机械安装、传感器与 I/O、算力、电源、通信、固件、SDK、许可、已有选件及允许改造边界。缺少官方或实测证据的字段标记未知。
3. 先独立定义场景需求和最低合格指标，再逐项映射本体能力，使用 `适配 / 条件适配 / 冲突 / 未知` 记录结论。不得降低或改写需求来制造虚假适配，也不得把厂商宣传等同于现场能力。
4. 发现安全、物理可达性、载荷、稳定性、环境等级、认证、实时控制或不可补偿接口等硬冲突时立即提示，不等到最终方案。说明证据、受影响的 Use Case、MVP 与验收，以及缩小场景、环境改造、外围增配、软件补偿、人工协作或重新确认需求等处置选项。
5. 锁定本体时不把更换本体写成推荐基线；只有用户允许换型或已证明不存在可接受闭环时，才把替代本体列为升级决策。条件适配必须给出成本、周期、风险、PoC 和失效后的降级路径。

需要记录本体基线、能力映射和冲突处置时，读取 [SCOPE-AND-REQUIREMENTS-FORMAT.md](./references/SCOPE-AND-REQUIREMENTS-FORMAT.md) 的既有本体章节。每个 阶段门 都复核当前阶段新增需求是否改变适配结论。

## 系统分层与团队责任边界

定义方案责任时必须读取并执行 [RESPONSIBILITY-BOUNDARIES-FORMAT.md](./references/RESPONSIBILITY-BOUNDARIES-FORMAT.md)。先定义 L1 机器人平台与本体、L2 机器人自主与技能、L3 任务智能与 Agent 的运行时权限，再映射本体、算法、AI 或供应商团队；组织可以合并层级，但接口和安全边界不能消失。

L3 只做任务分解、长程规划与 Skill 调度；L2 负责感知、导航/操作规划、直接动作 VLA、技能验证和局部恢复；L1 负责驱动、实时控制、轨迹执行、设备健康及不可绕过的限幅和停机。调用只能沿 `L3 → Skill API → L2 → Capability/Motion API → L1` 下行，状态和证据逐层上行；Agent 不得直接发送电机、关节、速度或轨迹命令。每项关键能力必须有唯一 Accountable，未解决的安全权限、越权路径或关键接口责任空洞阻塞 阶段门-6。

## 阶段转换确认

八个阶段都使用显式用户确认，不自动跨阶段。SOP 八步与七个阶段门加一个方案书阶段的映射关系如下：

| 阶段门 | 阶段名称 | 对应 SOP 步骤 | 核心产出 |
| --- | --- | --- | --- |
| 阶段门一 | 场景定义与 5W | 步骤 1–5：5W 定界、状态建模、故事板展开 | Use Case 清单、场景基线、状态机骨架、故事板与发现台账 |
| 阶段门二 | 范围冻结与责任分配 | 步骤 4（前半）：范围冻结 | 范围基线、Must/Should/Could/Out、需求清单 |
| 阶段门三 | 工程指标与定量推导 | 步骤 5：参数推导 | 硬件能力需求、软件责任需求、工程指标预算 |
| 阶段门四 | 系统方案决策 | 步骤 6：方案决策 | 候选比较、推荐系统方案、硬件 BOM、安全与责任边界 |
| 阶段门五 | 软件算法方案 | 步骤 7–8：软件算法、语音交互 | 软件架构、AI 感知、导航操作、语音方案、数据闭环 |
| 阶段门六 | MVP、PoC 与实施 | 步骤 9–10：MVP 收敛、PoC、实施阶段、验收标准 | MVP 定义、PoC 合同、实施计划、验收标准 |
| 阶段门七 | 方案书汇编 | 步骤 8：方案书定稿 | 正式项目方案书终稿 |

映射关系说明：SOP 的八步是分析主线，阶段门是确认节点。SOP 步骤 1–5 的结果在阶段门一中一次性确认（因为 5W、状态机和故事板相互依赖，单独确认价值低）。步骤 4 的范围冻结和步骤 5 的定量推导分别拆为阶段门二和三，因为范围冻结必须在选型前完成，且定量推导可能暴露需要回到步骤 4 修订的指标。步骤 6 的方案决策和步骤 7–8 的软件/语音方案拆为阶段门四和五，因为软件方案依赖系统方案已确认。步骤 9–10（MVP、PoC、实施、验收）合并为阶段门六，因为它们是同一决策层级的产物。步骤 8 的方案书汇编单独作为阶段门七，必须在前六个阶段门全部通过后才能执行。

当一个阶段达到可评审状态时，先停止后续分析，不生成下一阶段问题或方案，并输出：

```md
## 阶段门-{阶段编号}：{阶段名称}

- 本阶段已确认：
- 关键证据或产物：
- 既有本体适配结论：不适用 / 适配 / 条件适配 / 冲突 / 未知
- 责任边界结论：已确认 / 部分确认 / 存在关键空洞 / 本阶段不适用
- 阻塞项：无 / {列表}
- 非阻塞遗留项：无 / {列表及后续去向}
- 建议：继续当前阶段 / 进入下一阶段，以及原因

请选择：
1. 继续当前阶段（请说明希望补充或修改什么）
2. 确认当前阶段并进入下一阶段
```

存在会改变阶段结论的阻塞项、未处置的本体硬冲突或当前阶段必须解决的关键责任空洞时，不得推荐进入下一阶段，但仍保留两个选择并解释风险。用户选择继续时，只处理当前阶段，不偷跑下一阶段；用户明确选择 2 后，记录确认日期、确认内容、适配与责任边界结论和遗留项去向，再进入下一阶段。用户在任务开始时说“完成全流程”不构成八次阶段转换授权，每个 阶段门 必须基于当时实际产物单独确认。

逐题模式在当前轮只询问 阶段门 选择；批量模式把 阶段门 作为独立批次，不与下一阶段问题混发。阶段确认是可修订基线而非不可撤销承诺；前提变化时回到相应阶段，记录变化及对后续产物的影响。只有阶段门六无阻塞、无待确认关键决策且三份源文档一致时才能进入阶段门七；阶段门七使用“继续当前阶段 / 确认方案书终稿及 Discovery 完成”作为最终选项。

### 阶段门证据充分性检查

每个阶段门在允许阶段转换前，必须通过以下最低证据门槛。证据不足时不得推荐进入下一阶段，即使在推荐基线模式下用户已确认推荐答案：

| 阶段门 | 最低证据门槛 |
| --- | --- |
| 阶段门一 | 至少 1 项来自现场观察或测量的证据，或至少 1 项来自用户主动提供（非确认推荐）的决策；关键未知项有验证计划和责任人 |
| 阶段门二 | 任务状态机骨架覆盖所有已确认 Use Case，每个状态有进入/退出条件，终态和停止行为已区分 |
| 阶段门三 | 故事板至少覆盖主成功路径和所有已识别异常路径；发现台账中每个发现分配了类型（REQ/DEC/HYP/RISK/POC） |
| 阶段门四 | 所有 Must 需求有唯一 REQ ID；每个需求分配了 L1/L2/L3 责任和硬件/软件/人员/设施责任 |
| 阶段门五 | 每个影响选型的指标有公式、输入来源、最低/目标/理想值和设计余量；经验阈值已标记为 HYP |
| 阶段门六 | 至少比较两个端到端方案；所有硬件型号/软件版本有联网检索证据和事实截止日期；每个决策有适用条件、失败模式和换型条件 |
| 阶段门七 | 所有 PoC 有样本量、通过线、零容忍项和失败替代方案；实施阶段有周期区间、退出标准和关键依赖 |

证据不足时，阶段门确认输出中阻塞项必须列出缺少的具体证据，并在“建议”中说明“继续当前阶段”而非“进入下一阶段”。

### 单次会话阶段门跨越限制

单次会话（同一对话上下文）最多跨越 2 个阶段门。即使重复选择“2”确认，在跨越 2 个阶段门后必须停止并提示用户：

> 本轮已完成阶段门 X 和阶段门 Y 的确认。为避免关键事实被遗漏，建议在下一轮对话中重新确认这些事实是否仍然成立，再继续推进。是否继续下一阶段门？

该限制的目的是防止用户在短时间内连续确认多个阶段门而忽略关键证据缺口。用户明确表示需要加速时，可以例外但必须保留额外风险提示和证据欠账清单。

## 交互模式

在提出第一个需求问题前，先确认当前是否处于需求调研阶段。需求调研阶段的特征是：用户带着模糊场景开始、需要大量问答来收敛边界。如果用户已经跳过调研直接要求出方案，先确认"这个方案是基于已有调研结论，还是需要先梳理一下场景？"

如果用户确认需要梳理场景，确定交互模式。用户已经说明偏好时直接采用，不重复确认；无法判断时只问一次：

> 接下来会有一系列问题来收敛场景。你希望每次只问一个问题，即时回答；还是每次整理一批问题，你转发给相关人员回答？

| 用户选择 | 采用模式 |
| --- | --- |
| 每次一个问题 | 逐题模式 |
| 一批问题 | 批量模式 |

### 逐题模式

- 每轮只问一个核心问题；只有多个问题必须一起回答才能作出同一决策时，才组合为最多三个紧密相关的问题。
- 得到回答后立即镜像理解、更新事实与未知项，再选择下一个最高影响问题。
- 用户暂时不知道时，提供候选答案、反例或现场验证方法，不跳过确认直接替用户决定。
- 不提前展示后续长问卷，让谈话围绕当前最关键决策自然推进。

### 批量模式

- 每批默认提出五到八个高价值问题，最多十个；问题不足时不为凑数量补问低价值内容。
- 每批只覆盖一到两个相邻决策主题，优先处理会改变业务目标、场景边界、安全、MVP 或验收的未知项，不发送完整分析框架形成的大问卷。
- 使用稳定编号 `Q{批次}.{序号}`。每题标注 `必答` 或 `选答`，说明"为什么问"，提供二到四个候选答案、例子或反例，并保留自由补充入口。
- 只有会阻塞场景边界、安全或 MVP 的问题才标为必答。需要查数据、找材料或现场测量的问题，明确建议的证据和负责人，不要求用户凭印象回答。
- 不得在同一批次中并列强依赖问题。如果后一个问题必须基于前一个答案才能成立，将其留到下一批；可以用清晰的条件分支代替，例如"如果 Q1.2 选择营业中运行，再回答 Q1.3"。
- 在批次末尾提供可复制的编号答复模板，方便转发填写。模板可以独立复制粘贴，不依赖对话上下文。
- 收到部分回答时，先吸收已回答内容，把未回答项保留为未知，不要求重新填写整个批次。只对仍然阻塞当前阶段的未回答项追问。

批量模式使用以下最小结构：

```md
## 第 {n} 批：{本批决策主题}

### Q{n}.1（必答）{问题}

- 为什么问：{影响的范围、风险或验收决策}
- 候选答案：A. {选项} / B. {选项} / C. 其他
- 你的回答：

## 答复模板

- Q{n}.1：
- Q{n}.2：
- 补充材料：
```

收到部分回答时，先吸收已回答内容，把未回答项保留为未知，不要求用户重新填写整个批次。只对仍然阻塞当前阶段的未回答项追问；发现答案矛盾时，单独列出冲突及需要谁确认，不自行选择。

每批回复后先给出批次复盘：本批确认或修正的事实、仍未回答的高影响问题、发现的矛盾、已收到或缺少的证据，以及下一批准备收敛的决策主题。不要重复已经确认的问题。

用户可以在同一 slug 中随时切换模式，例如现场逐题会后把遗留问题转为批量分发，或收到批量答复后用逐题对话解决矛盾。切换时继承已有事实、假设、问题编号和证据，不重新开始需求发现。

### 推荐基线模式

当用户明确表示“无法回答当前问题”或“希望先看一套推荐方案”时，启动推荐基线模式。此模式是逐题/批量模式的补充，不是替代：

- 为当前批次的关键决策点给出一套完整推荐答案，每个推荐附推荐理由和最少验证门槛。
- 推荐答案统一标记为 `产品决策`（而非已确认事实），不得与用户主动提供的证据或现场测量数据混淆。
- 用户整体确认推荐后，在批次复盘中专设一个“推荐采纳统计”小节，明确记录：本批推荐答案总数、来自用户主动回答的数量、来自 AI 推荐的数量、缺少硬证据的项和有证据的截止日期。
- 如果到截止日期仍无证据，对应推荐答案降级为“未验证假设”，并在后续阶段门中列为阻塞项。
- 推荐基线模式不得跳过批量模式的必答问题标注——每道推荐答案必须说明“为什么推荐”“如果选其他答案会怎样”和“需要什么证据来验证”。
- 用户采纳推荐后，仍需在后续阶段门中逐项收口；不得因用户同意推荐而跳过阶段门证据检查。

推荐基线模式的批次复盘额外包含：

```md
### 推荐采纳统计

| 项目 | 数量 |
| --- | --- |
| 本批推荐答案总数 |  |
| 来自用户主动回答 |  |
| 来自 AI 推荐 |  |
| 缺少硬证据的项 |  |
| 硬证据截止日期 |  |
```

## 引导启发式交互

两种模式都不要把下面的分析框架机械变成长问卷。根据当前信息，寻找“回答后最可能改变场景边界、MVP 或可行性判断”的决策点；逐题模式逐个推进，批量模式按低依赖关系组成批次。

逐题模式每轮、批量模式每个问题都遵守以下启发合同：

1. **镜像理解**：用一到两句话复述刚确认的事实，并指出仍含糊的词，不重复用户已经回答的内容。
2. **说明目的**：明确这一轮要收敛什么决策，以及答案会影响范围、现场条件、风险还是验收。
3. **提出核心问题**：一个问题只服务一个主要决策，避免把多个不相关问题藏在同一句话中。
4. **提供认知脚手架**：给出二到四个贴近当前业务的候选答案、对比例子或反例，并说明差异。候选项必须允许用户修改或补充，不能伪装成唯一答案。
5. **给出条件化建议**：证据足够时给推荐项并解释依据；证据不足时给验证方法，不替用户确认事实。
6. **等待确认**：得到回答后更新事实、假设和未知项，再选择下一决策点；批量模式先完成本批复盘，再生成下一批。

用户要求直接出草案时可以继续，但必须显著标记待确认假设，并按所选模式给出后续澄清入口。

优先使用这些启发方式：

- **具体化**：把“整理好”“自主完成”“准确识别”改写为可观察状态，请用户选择或修正。
- **二选一压边界**：用两个会导致不同方案的具体情境暴露边界，例如营业中运行还是闭店后运行。
- **反例检验**：构造一个不应成功或必须人工介入的案例，检验目标状态是否完整。
- **最小闭环**：追问“如果第一版只能完成一个环节，哪个环节仍然有独立价值？”
- **证据回溯**：追问一个判断来自客户原话、现场观察、数据还是推测，并据此分类。事实按来源分为三类：`已确认事实`（需要物理证据如测量、照片、数据）、`产品决策`（用户确认的设计选择，来自推荐基线或口头确认，但无数据支撑）、`待验证假设`（需要后续 PoC 或现场调研才能确认）。三者不得混用。
- **状态回放**：让用户按触发、执行、完成、失败和恢复顺序回放一次真实任务。

## Use Case、故事板与状态机合同

用 Use Case 组织独立业务目标，不把产品的所有能力塞进一条 SOP。出现多个目标、参与者、触发方式或运行时段时，先建立 Use Case 清单，再逐个分析；简单单用例场景可以省略额外的 Use Case 关系图，但不能省略任务状态机图和状态转换表。

1. 把机器人视为待设计系统，把发起、协作、受影响、异常处理和负责的人员或外部系统记为 Actor；不要只把“机器人”写成 Who。
2. 每个 Use Case 定义业务目标、主要与次要 Actor、触发、前置条件、主成功路径、替代与异常路径、成功后置条件、取消/超时/安全停止、明确不处理项和待验证假设。此阶段只写结果与可观察行为，不绑定实现。
3. 同时使用正向对象和负向对象压实边界，例如“拿玩具，但不拿书籍和家具”。当“识别玩具”“识别新出现物品”“按对象清单判断”等定义会导出不同能力时，作为候选规则让用户确认。
4. 对每项自动化追问人工完成是否损害核心价值；优先自动化真实痛点，避免为低收益的触发判断、全局知识或泛化范围增加复杂度。
5. 用故事板把主成功路径展开为用户可观察的画面或文字步骤，再转成 SOP。为每帧分配稳定 ID，标记用户、机器人传感器、俯视规划、操作近景或环境状态等视角；逐帧提取机器人可获得的信息、对象与空间关系、决策、动作、输出状态、成功证据以及新发现的需求、能力、指标、决策、假设、风险和 PoC。不得用“清理中”“工作中”等大步骤掩盖搜索、接近、操作、验证和恢复。
6. 为任务状态机同时建立 Mermaid `stateDiagram-v2` 图和状态转换表；图展示状态、转换、分支、循环、并发与终态，表至少记录转换 ID、当前状态、事件、Guard、动作、下一状态、超时/重试、失败处理和成功证据。按任务、移动、操作、交互和安全监督分层，避免一个巨型状态机；横跨多个任务状态的避障、急停或健康监控建为并行监督行为。
7. 明确 Use Case 之间的包含、依赖、互斥、可并发和抢占关系。即使业务会话被禁用，暂停、停止、人工接管和安全告警等控制通道也可能必须始终可用。
8. 把“持续一段时间未发现目标”等终止条件标记为假设，并结合区域覆盖、不可达区域、漏检风险、跳过对象和人工确认定义完成证据。区分正常取消、安全停机、保护停止、紧急停止和意外断电。
9. 当一帧包含多个重要动作、成功证据不清、高风险失败、多个子系统协作、关键选型影响或抽象词时，使用子编号递归展开；当输入、输出、成功、失败和可推导能力已经明确时停止。跳过开机、待机等无需视觉分析的简单帧。
10. 把逐帧发现写入故事板发现台账并追踪到访谈问题、需求、工程指标、技术决策、风险、PoC 或验收；画面符号只能证明可观察结果，不能直接证明必须使用分割、深度相机、机器学习或其他实现。

需要建立 Use Case 清单、单用例合同、故事板或状态机时，读取并按 [USE-CASE-AND-BEHAVIOR-FORMAT.md](./references/USE-CASE-AND-BEHAVIOR-FORMAT.md) 写入 `spec/discovery.md`。任务状态机必须同时提供 Mermaid 图和状态转换表；图便于理解，表是评审、验收和软件规格的事实来源，两者必须一致。

## 范围基线与需求分配合同

在故事板和状态机稳定后冻结范围基线，再进入具体选型。读取并按 [SCOPE-AND-REQUIREMENTS-FORMAT.md](./references/SCOPE-AND-REQUIREMENTS-FORMAT.md) 把结果写入 `spec/discovery.md`，使用同一组 `REQ ID` 贯穿 Solution 与 Software Specification。

1. 为每个候选项记录来源、缺失影响和生命周期阶段，再分类为使命需求、使能需求、质量需求、安全/合规需求、既有约束、方案假设/决定或 desirement。需求类型与优先级是两个独立维度；使能或安全需求也可以是 Must。
2. 优先级使用 Must、Should、Could、Out。没有 Use Case、风险、法规、交付或生命周期依据的运行条件和功能默认不进入 MVP；不得用“保持最小范围”删除安全、维护、日志、标定或人工接管等必要闭环。
3. 对每项自动化追问没有它会让什么任务或验证失败、是否存在更简单的人工替代，以及扩大照明、对象、地域、语言或泛化范围的证据。desirement 保留价值说明但不伪装成需求。
4. 把遥操作、数据采集、标定、开机自检、诊断、日志、部署和维护等放入明确的开发、调试、训练、试点、运行或维护阶段；必要时建立生命周期 Use Case，并定义权限、安全限速、断连和审计边界。
5. 先从动作推导硬件能力和工程指标，再选择组件。底盘、机械臂、传感器、计算、通信、电源、安全和物理集成需求不得直接写成某个型号；选型产生的电压、接口和版本进入方案约束。
6. 按软件责任域整理启动健康、驱动控制、通信遥操作、感知世界模型、导航操作、任务编排、安全监督、交互、数据模型和运维需求。安全关键行为描述可验证结果，不预设必须使用学习算法。
7. 每条需求先分配到 L1/L2/L3 或跨层责任，再映射到硬件、软件、人员、设施、外部系统和真实团队；明确唯一 Accountable、共同 Responsible、输入输出、性能、安全边界和验证方式，软硬件共同承担的需求不得强行只归入一侧。
8. 新范围必须记录来源、价值或强制依据、对硬件、软件、成本、周期和验收的影响、替代方案、批准人以及进入当前 MVP 还是后续候选。
9. 指定本体是既有约束而不是需求来源；使用适配矩阵保留“场景所需能力”与“本体已有能力”的差值，并把增配、环境改造、软件补偿和人工责任分别追踪。

## 方案证据与选型合同

进入具体方案前，先确认业务目标、目标状态、关键对象、现场边界、安全等级和 MVP 闭环已经达到可用于选型的稳定程度。仍有缺口时继续给出推荐基线，但必须列明假设、受影响决策和验证门槛。

具体选型遵守以下合同：

1. 在形成任何具体硬件、软件、模型或云服务推荐前必须实时联网检索，先发现截至当日的新方案和版本，再核对官方产品页、数据表、论文、模型卡、代码仓库、API 文档、发行说明、许可、认证和标准；记录检索日期、事实截止日期、查询范围和链接，不能只依赖模型记忆或旧项目资料。
2. 建立“场景需求 → 工程指标 → 候选组件 → 证据 → 风险 → 验证方法”追踪链，不从热门产品或熟悉技术反推需求。
3. 有多个可行选项时至少比较两个候选；给出一个推荐基线、备选方案和淘汰理由。锁定本体时比较至少两个有意义的适配路径，而不是强行比较其他本体。
4. 未指定本体时，对机器人本体、机械臂、末端执行器、传感器、算力和安全组件给出具体厂商与型号。已指定本体时，把准确型号和配置写成既有基线，围绕它推荐新增组件与集成方案；关键约束不足时给条件化结论和换型触发条件。
5. 参数比较至少覆盖与场景相关的载荷、工作空间、精度、速度、尺寸、环境适应性、安全、接口、算力、功耗、维护、供货和成本。没有可靠证据的字段标记 `待供应商确认`，不补造数字。
6. 价格、供货周期、软件版本和产品状态具有时效性，必须注明地区、币种、日期和来源；只有非约束性区间时不得写成正式报价。
7. 把厂商声明与 PoC 实测分开。涉及人身协作、食品、医疗、高处、重物或危险环境时，明确需要安全、法规或现场工程负责人复核。
8. 每个关键技术决定都说明推导过程、适用条件、失败模式、降级路径和替换边界。

无法联网或无法访问关键官方资料时，可以继续需求、架构和 PoC 草案，但不得宣称技术选型最新或完成；把在线检索列为阶段 6 阻塞项。快速变化的软件、AI 模型和开发平台必须核对准确版本、发布日期、GA/EA/Preview/研究状态、维护活跃度、许可、可获得性和已知限制，不用“最新”“先进”代替证据。

## VLA 与快速演进 AI 方案选型

只有场景证据表明需要语言条件控制、跨任务/对象泛化或机器人基础模型能力时才进入 VLA 选型。进入后必须读取并执行 [VLA-SELECTION-FORMAT.md](./references/VLA-SELECTION-FORMAT.md)：实时联网建立候选集，在存在足够合格方案时比较至少三个 VLA 候选，同时保留模块化非 VLA 基线和传统学习策略，不得只评估 OpenVLA 或任何单一熟悉模型。

候选优缺点必须关联当前 Use Case、指定本体、动作空间、控制频率、相机与状态输入、数据预算、算力、网络、安全、许可和交付条件。区分直接输出动作的 VLA、高层具身推理/VLM、世界模型和数据生成工具；跨论文 benchmark 只有在任务、本体、数据和评测协议可比时才能排序。输出一个推荐基线、主要备选、排除理由、切换条件以及同条件 PoC；若合格 VLA 不足三个，列出检索到但被排除的方案与证据。

## 定量工程推导合同

对会直接影响器件选型、成本、安全或任务成功率的指标执行定量推导，不只引用经验值。按以下顺序形成可复核计算：

1. 从任务 SOP 选择代表性对象，以及必须覆盖的最不利但合理工况；不要把多个低概率极端条件无依据地叠加。
2. 区分发现、检测、分类、实例识别、定位、姿态估计、抓取和结果验证等不同任务；分别定义其有效距离和成功指标，不共用一个笼统阈值。
3. 为距离、精度、延迟或其他关键指标给出“最低可接受值 / 目标值 / 理想值”。通过反例或思维实验说明低于最低值为何导致任务不可用，以及理想值是否值得增加成本。
4. 选择适用的几何、光学、运动学、动力学、带宽、时延或功耗模型，写明公式、单位、输入来源、适用范围和简化假设。模型不确定时并列计算或安排测量，不混用不同模型的结果。
5. 计算候选方案的结果和设计余量，执行敏感性分析，指出哪个输入最可能触发换型。计算结果不得替代厂商参数核对、标定和实测。
6. 把未经目标模型和代表性数据验证的经验阈值记录为 `HYP-xxx`，说明依据、受影响决策和 PoC 通过门槛；不得把数据集名称或行业传言写成通用性能定律。
7. 使用官方数据表核对器件输入，通过标定、代表性样本、最不利工况和端到端 PoC 闭环验证，最后把结果区分为推导值、厂商声明和实测值。

相机选型至少检查任务类型与目标像素预算、最小目标、工作距离区间、目标在视场中的位置、投影和畸变模型、分辨率与视场权衡、帧率、曝光与运动模糊、镜头成像质量、焦距与景深、照明与动态范围、快门类型、接口带宽、同步、延迟、尺寸、重量、功耗、成本和环境等级。

对于理想无畸变的矩形投影相机，可用下面的中心区域近似做早期预算，其中目标宽度和距离必须使用同一单位：

```text
fx = image_width_px / (2 * tan(horizontal_fov / 2))
pixels_on_target ~= fx * object_width / optical_axis_distance
```

`image_width_px / horizontal_fov_deg` 只能作为线性角度近似，不能与矩形投影模型混算。鱼眼、明显畸变、画面边缘目标、裁剪或缩放后的图像需要使用相应投影模型和标定参数。

需要反复计算相机像素预算时使用 `./scripts/camera_pixel_budget.py`。该脚本只读取命令行参数并输出计算结果，默认行为即为只读 dry-run，不写文件、不访问网络，也没有 `--execute` 或 `--apply` 正式执行开关。输入尺寸和距离必须使用同一单位；输出只能作为设计预算，不能替代镜头标定和目标模型 PoC。

```bash
python3 {skill_dir}/scripts/camera_pixel_budget.py \
  --object-width 3 --distance 96 \
  --image-width 1024 --hfov-deg 90 \
  --required-pixels 35 --margin-percent 20
```

其中 `{skill_dir}` 是当前技能目录。需要机器读取结果时追加 `--json`；只有在明确需要比较粗略历史算法时才使用 `--model linear-angle`，并保留脚本输出的近似警告。

## 方案产物

访谈过程按 [INTERVIEW-FORMAT.md](./references/INTERVIEW-FORMAT.md) 持续写入 `spec/interview.md`。项目状态按 [STATUS-FORMAT.md](./references/STATUS-FORMAT.md) 维护 `STATUS.md` 仪表盘。场景基线写入 `spec/discovery.md` 后，继续生成两个相互引用的详细规格，最后汇编方案书：

- 按 [SOLUTION-SPECIFICATION-FORMAT.md](./references/SOLUTION-SPECIFICATION-FORMAT.md) 编写 `design/solution-specification.md`，负责系统级方案、具体硬件、BOM、部署、PoC、成本假设和实施里程碑。
- 按 [SOFTWARE-SPECIFICATION-FORMAT.md](./references/SOFTWARE-SPECIFICATION-FORMAT.md) 编写 `design/software-specification.md`，负责软件架构、底层通信、AI 与感知、规划控制、语音交互、数据与模型闭环、接口和测试。
- 两份规格完成、关键事项确认且一致性评审通过后，按 [PROPOSAL-FORMAT.md](./references/PROPOSAL-FORMAT.md) 编写 `design/proposal.md` 正式终稿，面向客户和项目决策评审呈现完整项目方案。

两个规格必须使用同一组需求 ID 和决策 ID，保持双向追踪，并共同采用同一份运行时分层、RACI、Skill API 与 Capability/Motion API 边界。Solution Specification 是系统与硬件详细规格，Software Specification 是软件与算法详细规格；出现矛盾时先修正源文档。方案书只能提炼一致的最终结论，不得覆盖或悄悄改写规格；仍有阻塞或待确认关键事项时不得生成方案书。

### 方案书内容边界

方案书是面向客户和决策者的业务文档，不是技术文档的合并。以下内容**严禁出现在方案书中**（它们属于 discovery.md 或 solution-specification.md）：

| 禁止内容 | 所属文档 | 方案书中的正确做法 |
| --- | --- | --- |
| 状态机图、状态转换表 | discovery.md | 引用一句话结论："任务流程已覆盖正常派送、电梯等待、异常中断等全部路径" |
| 故事板帧表 | discovery.md | 引用关键场景的一句话描述，不逐帧列出 |
| 范围冻结表（M/S/C/O） | discovery.md | 只写"本期做什么、不做什么"，不列完整范围表 |
| 工程指标推导过程、公式 | solution-specification.md | 只写最终指标和目标值，不展示推导 |
| 需求 ID 清单（REQ-001~XXX） | discovery.md | 只写关键需求描述，不列 ID |
| 候选方案评分矩阵 | solution-specification.md | 只写推荐方案和一句话理由，不列评分 |
| 内部简写（Y4、P1、B2、H1-H9 等） | 仅限调研对话 | 翻译为完整中文描述 |
| 方法论词汇（5W、阶段门、L1/L2、状态机） | 仅限内部 | 完全禁止 |

生成的方案书必须通过以下检查才能在"方案阶段"填写"终稿"：
- 通篇搜索不到"5W""阶段门""状态机""故事板""L1/L2""REQ-"等词汇
- 通篇搜索不到调研过程中产生的内部简写
- 以决策者视角通读全文，能在 5 分钟内理解"为什么做、做什么、怎么做、投入多少、多久交付、有什么风险"

## 分析流程

流程用于选择下一轮问题，不要求机械地逐章提问。如果已有材料能够回答，先从材料提取事实并标注出处。

### 1. 重述原始诉求

引用客户原话，用一句话重述要解决的问题，圈出不能直接开发或验收的词。例如“整理”可能指补货、归位、调整排面、盘点或清洁，先让用户确认，不自行合并。同时识别是否已有指定本体及其约束等级；本体型号明确不代表场景已经可行。

### 2. 确认业务问题

确认当前由谁完成、现行 SOP、最痛环节、任务频率与峰值、业务基线以及最希望改善的一个指标。缺少价值或基线数据时标记待调研。

### 3. 建立 Use Case 并用 5W 界定场景

先判断产品包含一个还是多个独立业务目标，建立 Use Case 清单并标记价值、Actor、优先级、MVP 归属及相互关系。再对每个 Use Case 使用 5W；此阶段不讨论实现技术。

| 维度 | 需要明确的内容 |
| --- | --- |
| Who | 发起任务、现场协作、被影响、异常处理和最终负责的人 |
| What | 操作对象、目标状态，以及明确不做什么 |
| When | 触发方式、运行时段、频率、时限和停止条件 |
| Where | 区域、通道、地面、照明、拥挤度和禁入区 |
| Why | 业务痛点、优先级、成功指标和可接受成本 |

此阶段先定义 `What`，暂不讨论 `How`。用正向对象、负向对象和候选判定规则澄清边界，并为每个用例定义触发、成功和退出条件。

### 4. 盘点现场与对象

只检查与当前任务相关的维度：

- 对象：品类、包装、尺寸、重量、软硬、透明或反光、易碎、可堆叠性和摆放规则。
- 空间：通道宽度、操作高度与深度、地面、坡度、门槛、电梯、充电点和待机点。
- 动态环境：顾客、儿童、员工、车辆、临时堆物和高峰时段。
- 任务与系统：任务来源、库存、货位、地图、主数据、权限和网络可用性。
- 合规安全：人身、食品、消防、隐私、碰撞、跌落、液体、高处和重物风险。

关键事实优先建议现场观察、照片或视频采样、实物测量和系统数据核对，不只依赖口头描述。

### 5. 定义目标状态

使用“对象 + 位置 + 状态 + 容差”描述结果。例如把“货架整理整齐”改为“将指定 SKU 放入对应货位，正面朝向通道，完全位于货架边界内，并满足已约定的间距容差”。目标不明确时提供候选定义请用户选择。

### 6. 建立初始状态机骨架

根据 Use Case 同时绘制任务级 Mermaid 状态机骨架并填写状态转换表，只包含开始、主要任务阶段、正常完成、失败、取消和人工介入。每个转换使用稳定 ID，先记录事件、已知 Guard 和成功证据；未知的内部行为留给故事板展开，不用“自主工作”或一个巨型状态代替分析。

### 7. 用故事板展开并修订状态机

按一次真实任务的时间顺序写出画面或文字故事板，逐帧检查机器人实际可获得的信息与真实环境信息之间的差距，并把发现写入台账。再从触发到结束按用户可观察的行为拆解。每一步记录：

| 字段 | 含义 |
| --- | --- |
| 输入状态 | 执行前必须满足的条件 |
| 动作 | 机器人或协作人员做什么 |
| 输出状态 | 成功后环境发生什么变化 |
| 成功判定 | 用什么证据判断成功 |
| 失败分支 | 失败、阻塞或不确定时怎么办 |

可从“接收任务 → 到达作业区 → 确认对象与目标位置 → 接近 → 操作 → 验证 → 汇报结束”开始，再按真实场景增删。

只递归展开仍含多个重要动作、风险、跨子系统协作或不明确成功证据的帧。故事板阶段发现的语音、相机、分割、机器学习或目标选择方法先记录为候选方案或假设，不能替代需求确认和后续选型。

用故事板发现同步修订状态机图和状态转换表，补齐状态、事件、Guard、转换、超时和重试，并按任务、移动、操作、交互与安全监督分层。检查对象或位置找不到、遮挡或阻塞、操作失败、结果验证失败、现场与系统不一致、网络或电量异常、碰撞风险、物品损坏和紧急停止。为每类情况明确自动重试次数、跳过并记录、请求人工确认或立即停止，禁止无限重试；交付前逐项核对图中边与表中转换 ID 一致。

### 8. 冻结范围、分配需求并推导工程指标

从 Use Case、故事板、SOP、状态机、风险和生命周期活动收集候选项，按“范围基线与需求分配合同”判断类型、优先级和 MVP 状态。再反推定位导航、对象识别、可达性判断、抓取放置、结果验证、任务调度、安全避障和人工接管等能力，把能力转为载荷、工作空间、定位精度、节拍、视场、距离、延迟、可用性、算力、网络和安全等级等指标；先分配 L1/L2/L3 运行时责任和唯一 Accountable，再映射硬件、软件、人员、设施、外部系统与真实团队。已有指定本体时逐项形成适配矩阵和冲突台账。对影响选型的指标执行“定量工程推导合同”，保留来源和验收方法。

### 9. 比较并选择系统方案

提出能够形成端到端闭环的候选架构，比较固定式、移动式、单臂、双臂、专机或人机协同等形态。未指定本体时按“方案证据与选型合同”完成本体及配套组件选型；锁定本体时比较围绕该本体的增配、环境改造、软件补偿和人工协同路径，形成现有/新增/改造 BOM、布置、接口、性能预算与残余缺口。

### 10. 编写软件与算法方案

定义 L1/L2/L3 组件归属、设备驱动、实时或底层控制、中间件、通信协议、Skill API、Capability/Motion API、任务编排、业务系统集成、数据模型和部署拓扑。详细说明 AI 与感知链路，包括数据来源、标注、检测或分割、位姿估计、跟踪、定位建图、抓取与运动规划、VLA 或大模型的适用边界、在线检索得到的多候选比较、模型评测、回退和人工接管。

### 11. 设计语音交互

需要语音时，定义麦克风与声学条件、唤醒、VAD、ASR、意图或 LLM、对话状态、TTS、打断、离线或云端策略、端到端延迟、隐私和安全确认。噪声环境或安全关键指令必须有非语音替代通道；不需要语音时写明排除理由。

### 12. 收敛 MVP 与 PoC

选择价值明确、环境相对稳定、对象有限且容易验收的最小闭环。明确 MVP 内、MVP 外与下一阶段候选，并为高风险硬件、感知、操作、语音、系统集成和本体适配冲突设计 PoC：样本、环境、步骤、指标、通过门槛、失败后的替代方案和责任人。

### 13. 规划实施阶段与里程碑

给出从现场勘查、采购与样机、基础集成、单能力 PoC、闭环联调、试点、验收和规模部署的阶段计划。每个阶段写明输入、输出、负责人、依赖、周期估算依据、退出标准和关键风险。日期和工期证据不足时使用相对周数或区间，并显式记录资源与供货假设。

### 14. 编写验收标准

每项指标必须包含测试条件、样本量、计算口径和目标阈值。按场景选择任务完成率、单步成功率、作业时间、人工介入率、错放漏放、损坏跌落、安全距离、语音任务成功率、连续运行时长和故障恢复时间。阈值没有证据时标记 `待客户确认`，不得只写“准确率高”或“运行稳定”。

### 15. 汇编最终项目方案书

确认 Discovery、系统与硬件规格、软件规格的范围、需求、型号、版本、指标、接口、责任、商务约定和里程碑一致，且所有关键决策与阻塞已经关闭后，按“方案产物”合同生成 `design/proposal.md` 正式终稿。方案书只呈现最终价值、方案、边界、配置、实施、验收、商务约定和责任，不包含访谈记录、问题清单、推导过程、候选比较、检索过程、内部检查或文档形成说明；条件不满足时回到对应阶段，不生成方案书。

## 需求发现文档

更新 `spec/discovery.md` 时读取并按 [DISCOVERY-FORMAT.md](./references/DISCOVERY-FORMAT.md) 组织内容。没有事实支撑的章节保留为简短未知项，不要猜测补齐；修订同一场景时继续使用同一 slug，并记录本轮确认及本体配置变化。

访谈过程按 [INTERVIEW-FORMAT.md](./references/INTERVIEW-FORMAT.md) 写入 `spec/interview.md`。discovery.md 中只保留访谈方式摘要和批次复盘关键结论，完整问题、回答和来源追踪都在 interview.md 中。两文件通过批次编号和证据 ID 保持关联。

## 完成标准

- 已说明客户为何需要机器人，而不只是机器人要做什么。
- 已区分客户原话、确认事实、待验证假设和未知项，并为关键未知项安排验证方法。
- 已把抽象目标改写为可观察的环境状态，定义开始、完成、失败和停止条件。
- 已识别独立 Use Case、Actor、触发、前后置条件、正负边界和用例关系；未把机器人误当成唯一 Actor。
- 已形成可回放的任务 SOP，并覆盖人员协作、安全、异常、重试和人工接管。
- 关键故事板帧已标记视角、可获得信息、空间条件和成功证据；逐帧发现已进入台账并追踪到需求、决策、风险、PoC 或验收，复杂帧已按门槛展开。
- 已用图形和表格建立任务状态机骨架，再通过故事板同步修订；图中状态与边、表中转换 ID、Guard 和终态一致，横切监督行为、并发/互斥关系以及正常停止与安全停止已经区分。
- 已冻结范围基线，区分使命、使能、质量、安全、既有约束、方案决定和 desirement；类型、优先级、生命周期和 MVP 状态可追踪。
- 硬件能力与软件责任从同一组需求推导并分配到所有责任方；组件型号没有被伪装成原始需求，范围变化已有影响和批准记录。
- 已定义 L1/L2/L3 运行时边界、真实团队 RACI、规划与 VLA 归属、禁止调用路径及 Skill/Capability 接口；关键能力有唯一 Accountable，平台安全可独立拒绝或停机。
- 存在指定本体时已确认约束等级、准确配置、证据与改造边界，并逐项给出适配、条件适配、冲突或未知结论；硬冲突已经告警并得到处置决定。
- MVP 构成端到端闭环，范围足够小，且明确列出暂不支持项。
- 验收标准可以在指定现场条件下重复测试，未确认阈值被显式标记。
- 场景基线稳定后已给出一个具体推荐系统方案、至少一个有意义的备选及淘汰理由；硬件型号、关键参数和软件版本都有证据或明确的待确认标记。
- 已覆盖底层与通信、软件架构、AI 与感知算法、导航或操作、语音交互、业务集成、数据闭环、降级和测试方案。
- 所有时效性技术选型均已在本轮联网核对并记录事实截止日期；采用 VLA 时已比较至少三个合格候选、非 VLA 基线和传统学习策略，或说明候选不足的排除证据。
- 已建立需求、工程指标、组件、技术决策、证据和验证项之间的追踪关系。
- 关键选型指标已记录计算模型、单位、输入来源、最低/目标/理想值和设计余量；经验阈值被标记为假设并安排代表性 PoC。
- 已给出 PoC、实施阶段、周期区间、里程碑、退出标准、关键依赖和风险；未经验证的能力没有写成确定承诺。
- 每个已跨越阶段都有独立用户确认记录；未确认 阶段门 没有被开始时的全流程请求或 Agent 自行判断跳过。
- `team-spec/active/{slug}/spec/interview.md` 已创建并持续更新，包含所有批次问题、回答来源、批复盘、全局证据清单和未决问题清单。
- `team-spec/active/{slug}/spec/discovery.md` 已创建或更新，并记录本轮 Change Log。
- `team-spec/active/{slug}/design/solution-specification.md` 已创建或更新。
- `team-spec/active/{slug}/design/software-specification.md` 已创建或更新。
- `team-spec/active/{slug}/design/proposal.md` 已基于前三份一致产物，按 [PROPOSAL-FORMAT.md](./references/PROPOSAL-FORMAT.md) 统一模板生成，版本号完整，不含过程性内容、待确认关键事项或未解除阻塞。
- `team-spec/active/{slug}/STATUS.md` 已按 [STATUS-FORMAT.md](./references/STATUS-FORMAT.md) 创建并持续更新，仪表盘内容与当前产物一致。
- 风险登记册已建立，每条 Must 需求的风险为高或严重时，有对应的缓解措施和负责人。
- 需求追溯矩阵已建立，每条 Must 需求至少有一条设计决策、一个覆盖组件和一个验证 PoC。

如果关键业务目标、目标状态、现场安全边界或 MVP 闭环仍未知，不要宣称完整方案完成；说明当前成熟度并继续引导。关键选型事实不足时仍给出条件化推荐基线，但不得把它描述为已验证或可直接采购的最终结论。

## 最终回复

逐题模式每轮回复保持短小，包含：

1. 本轮确认或修正了什么。
2. 当前最关键的决策点及其影响。
3. 一个核心问题、候选答案或验证建议。

批量模式每批输出包含：

1. 当前已知事实、待验证假设和本批目标的简短摘要。
2. 五到八个带稳定编号、必答/选答、提问原因和候选答案的问题；确有必要时最多十个。
3. 可复制的编号答复模板和需要附带的材料说明。
4. 收到答复后的批次复盘；部分回答不得被丢弃或要求整批重填。

阶段达到可评审状态时，逐题和批量模式都改用“阶段转换确认”格式；未收到选择前结束当前轮，不附带下一阶段内容。

需求发现达到完成标准或用户要求阶段性收口时，最终回复包含：

- 场景目标、最终系统方案、适用范围和明确不支持项。
- `design/proposal.md` 终稿的路径、版本、事实截止日期和生效范围，以及三个详细源文档路径。
- 最终机器人、末端执行器、传感器、算力与软件算法栈配置。
- 已有指定本体时，说明最终适配、必要增配或改造和已接受的运行边界。
- L1/L2/L3 责任、团队/供应商分工、Agent 与技能调用权限和安全裁决边界。
- PoC、实施阶段、周期、里程碑、验收、成本口径和主要风险摘要。
- 阶段性收口但尚未满足终稿条件时，明确说明不生成 `proposal.md`，并列出需要返回处理的阶段。
- 本技能范围内的下一步选项，通常包括补充现场证据、继续当前阶段、评审或调整四份产物、执行 PoC，或者确认方案书及本次 Discovery 完成；不推荐或自动进入其他技能。
