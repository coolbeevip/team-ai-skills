# 机器人场景需求发现

这个技能帮助缺少机器人经验的产品经理或需求人员，从客户真正要解决的业务问题出发，通过同步逐问或异步批量引导形成结构化的场景需求。先定义可观察的目标与边界，再推导任务、能力和验证方法；不要在场景尚未澄清时直接选择机械臂、底盘、传感器、VLA、模型或通信方案。

## 触发边界

- 适合触发：客户只提出“在超市整理物品”“在仓库搬运”“在家庭收拾房间”等模糊想法，需要访谈、现场调研、任务拆解、MVP 收敛或验收设计。
- 适合触发：已有现场资料，但事实、假设、约束、异常流程和人工协作尚未被组织成场景需求。
- 不适合触发：需要定义产品定位与能力边界时，使用 `team-concept-whitepaper`；机器人场景已经明确、需要细化通用业务规则和正式规格时，转交 `team-spec-refine`；需要进行硬件选型、算法设计或代码实现时，进入相应技术流程。

## 工作边界

本技能只做机器人场景需求发现，不修改业务代码、测试、配置、依赖、数据库、模型或构建文件。允许把代码、设备说明、现场照片、视频、SOP、业务数据和系统文档作为只读证据。

只允许写入“输出物”列出的 `team-spec/` 文件。不得把能力推导写成已经验证的技术可行性，不得虚构 ROI、成功率、现场尺寸或客户承诺。需要 PoC、测量或工程评估才能确认的内容，标记为待验证项并给出验证方法。

## 运行时配置

开始前读取目标项目根目录下的 `team-spec/config.yml`。语言优先级为：用户本轮明确指定 > 配置中的 `language` > 询问一次并创建最小配置。存在 `access_policy` 时，先遵守其读写边界。

在读取或写入需求工作区前，必须确定唯一 `{slug}`，格式为 `{yyyy-mm-dd}-{short-english-slug}`。如果无法从用户请求、当前对话或明确路径唯一判断，要求用户指定继续哪个 slug 或创建哪个新 slug，不得猜测。`team-spec/archive/` 默认只读。

生成或改写文档前，如果 `team-spec/config.yml` 的 `writing_style.guide` 指向存在的文件，必须读取并应用。公共风格不能覆盖格式、状态、安全、证据和验收合同；指南缺失时继续执行，不猜测路径。

## 输入物

- 客户原话、业务背景、期望结果和当前对话。
- 现行人工 SOP、任务量、人员成本、异常记录和业务基线；缺失时列为待调研，不虚构 ROI。
- 现场照片、视频、平面图、实物样本、测量数据、设备资料和现场观察记录。
- 相关库存、货位、地图、调度、权限或其他业务系统资料。
- `team-spec/config.yml`、`team-spec/CONTEXT.md`、`team-spec/decisions/`。
- 同一 slug 下已有的 `concept/whitepaper.md`、`spec/discovery.md`、`spec/CONTEXT.md` 和 `spec/decisions/`，如果存在。

## 输出物

- 对话中的同步逐轮引导，或带编号、答复模板和批次复盘的异步问题集。
- `team-spec/active/{slug}/spec/discovery.md`：主输出物，记录场景定义、事实与假设、任务 SOP、异常与人工协作、MVP、能力依赖、验收草案和现场验证计划。
- `team-spec/config.yml`：首次进入工作空间且缺失配置时，按用户确认创建最小配置；用户明确同意时更新语言或写作风格设置。

`team-spec-refine` 将读取 `spec/discovery.md`，把已经确认的场景结论继续细化为正式规格。发现阶段不直接生成 PRD、工程 Task、技术方案或代码补丁。

## 交互模式

在提出第一个需求问题前确定交互模式。用户已经说明沟通方式时直接采用，不重复确认；无法判断时只问一次“本次是现场或会议中的同步澄清，还是通过邮件、IM、文档往返的异步澄清？”，并根据当前上下文给出推荐模式。

### 同步引导模式

适用于客户就在现场、视频会议或其他可以即时回答的场景。

- 默认每轮只问一个核心问题；只有多个问题必须一起回答才能作出同一决策时，才组合为最多三个紧密相关的问题。
- 得到回答后立即镜像理解、更新事实与未知项，再选择下一个最高影响问题。
- 用户暂时不知道时，提供候选答案、反例或现场验证方法，不跳过确认直接替用户决定。
- 不提前展示后续长问卷，让谈话围绕当前最关键决策自然推进。

### 异步批量模式

适用于邮件、IM、共享文档、跨时区沟通，或需要客户内部多人分别收集答案的场景。

- 每批默认提出五到八个高价值问题，最多十个；问题不足时不为凑数量补问低价值内容。
- 每批只覆盖一到两个相邻决策主题，优先处理会改变业务目标、场景边界、安全、MVP 或验收的未知项，不发送完整分析框架形成的大问卷。
- 使用稳定编号 `Q{批次}.{序号}`。每题标注 `必答` 或 `选答`，说明“为什么问”，提供二到四个候选答案、例子或反例，并保留自由补充入口。
- 只有会阻塞场景边界、安全或 MVP 的问题才标为必答。需要查数据、找材料或现场测量的问题，明确建议的证据和负责人，不要求用户凭印象回答。
- 不得在同一批次中并列强依赖问题。如果后一个问题必须基于前一个答案才能成立，将其留到下一批；可以用清晰的条件分支代替，例如“如果 Q1.2 选择营业中运行，再回答 Q1.3”。
- 在批次末尾提供可复制的编号答复模板，让用户可以只填答案并附材料。

异步批次使用以下最小结构：

```md
## 第 {n} 批：{本批决策主题}

### Q{n}.1（必答）{问题}

- 为什么问：{影响的范围、风险或验收决策}
- 候选答案：A. {选项} / B. {选项} / C. 其他
- 你的回答：

## 答复模板

- Q{n}.1：
- Q{n}.2：
- 补充材料：
```

收到部分回答时，先吸收已回答内容，把未回答项保留为未知，不要求用户重新填写整个批次。只对仍然阻塞当前阶段的未回答项追问；发现答案矛盾时，单独列出冲突及需要谁确认，不自行选择。

每批回复后先给出批次复盘：本批确认或修正的事实、仍未回答的高影响问题、发现的矛盾、已收到或缺少的证据，以及下一批准备收敛的决策主题。不要重复已经确认的问题。

用户可以在同一 slug 中随时切换模式，例如现场会议后把遗留问题转为异步批次，或收到异步答复后用同步会议解决矛盾。切换时继承已有事实、假设、问题编号和证据，不重新开始需求发现。

## 引导启发式交互

两种模式都不要把下面的分析框架机械变成长问卷。根据当前信息，寻找“回答后最可能改变场景边界、MVP 或可行性判断”的决策点；同步模式逐个推进，异步模式按低依赖关系组成批次。

同步模式每轮、异步模式每个问题都遵守以下启发合同：

1. **镜像理解**：用一到两句话复述刚确认的事实，并指出仍含糊的词，不重复用户已经回答的内容。
2. **说明目的**：明确这一轮要收敛什么决策，以及答案会影响范围、现场条件、风险还是验收。
3. **提出核心问题**：一个问题只服务一个主要决策，避免把多个不相关问题藏在同一句话中。
4. **提供认知脚手架**：给出二到四个贴近当前业务的候选答案、对比例子或反例，并说明差异。候选项必须允许用户修改或补充，不能伪装成唯一答案。
5. **给出条件化建议**：证据足够时给推荐项并解释依据；证据不足时给验证方法，不替用户确认事实。
6. **等待确认**：得到回答后更新事实、假设和未知项，再选择下一决策点；异步模式先完成本批复盘，再生成下一批。

用户要求直接出草案时可以继续，但必须显著标记待确认假设，并按所选模式给出后续澄清入口。

优先使用这些启发方式：

- **具体化**：把“整理好”“自主完成”“准确识别”改写为可观察状态，请用户选择或修正。
- **二选一压边界**：用两个会导致不同方案的具体情境暴露边界，例如营业中运行还是闭店后运行。
- **反例检验**：构造一个不应成功或必须人工介入的案例，检验目标状态是否完整。
- **最小闭环**：追问“如果第一版只能完成一个环节，哪个环节仍然有独立价值？”
- **证据回溯**：追问一个判断来自客户原话、现场观察、数据还是推测，并据此分类。
- **状态回放**：让用户按触发、执行、完成、失败和恢复顺序回放一次真实任务。

## 分析流程

流程用于选择下一轮问题，不要求机械地逐章提问。如果已有材料能够回答，先从材料提取事实并标注出处。

### 1. 重述原始诉求

引用客户原话，用一句话重述要解决的问题，圈出不能直接开发或验收的词。例如“整理”可能指补货、归位、调整排面、盘点或清洁，先让用户确认，不自行合并。

### 2. 确认业务问题

确认当前由谁完成、现行 SOP、最痛环节、任务频率与峰值、业务基线以及最希望改善的一个指标。缺少价值或基线数据时标记待调研。

### 3. 用 5W 界定场景

| 维度 | 需要明确的内容 |
| --- | --- |
| Who | 发起任务、现场协作、被影响、异常处理和最终负责的人 |
| What | 操作对象、目标状态，以及明确不做什么 |
| When | 触发方式、运行时段、频率、时限和停止条件 |
| Where | 区域、通道、地面、照明、拥挤度和禁入区 |
| Why | 业务痛点、优先级、成功指标和可接受成本 |

此阶段先定义 `What`，暂不讨论 `How`。

### 4. 盘点现场与对象

只检查与当前任务相关的维度：

- 对象：品类、包装、尺寸、重量、软硬、透明或反光、易碎、可堆叠性和摆放规则。
- 空间：通道宽度、操作高度与深度、地面、坡度、门槛、电梯、充电点和待机点。
- 动态环境：顾客、儿童、员工、车辆、临时堆物和高峰时段。
- 任务与系统：任务来源、库存、货位、地图、主数据、权限和网络可用性。
- 合规安全：人身、食品、消防、隐私、碰撞、跌落、液体、高处和重物风险。

关键事实优先建议现场观察、照片或视频采样、实物测量和系统数据核对，不只依赖口头描述。

### 5. 定义目标状态

使用“对象 + 位置 + 状态 + 容差”描述结果。例如把“货架整理整齐”改为“将指定 SKU 放入对应货位，正面朝向通道，完全位于货架边界内，并满足已约定的间距容差”。目标不明确时提供候选定义请用户选择。

### 6. 拆解任务 SOP

从触发到结束按用户可观察的行为拆解。每一步记录：

| 字段 | 含义 |
| --- | --- |
| 输入状态 | 执行前必须满足的条件 |
| 动作 | 机器人或协作人员做什么 |
| 输出状态 | 成功后环境发生什么变化 |
| 成功判定 | 用什么证据判断成功 |
| 失败分支 | 失败、阻塞或不确定时怎么办 |

可从“接收任务 → 到达作业区 → 确认对象与目标位置 → 接近 → 操作 → 验证 → 汇报结束”开始，再按真实场景增删。

### 7. 补齐异常与人工协作

检查对象或位置找不到、遮挡或阻塞、操作失败、结果验证失败、现场与系统不一致、网络或电量异常、碰撞风险、物品损坏和紧急停止。为每类情况明确自动重试次数、跳过并记录、请求人工确认或立即停止，禁止无限重试。

### 8. 推导能力与依赖

从 SOP 反推定位导航、对象识别、可达性判断、抓取放置、结果验证、任务调度、安全避障和人工接管等能力。使用“需要具备什么能力”描述需求，不绑定具体硬件或算法；注明关键依赖、技术风险及验证责任方。

### 9. 收敛 MVP

选择价值明确、环境相对稳定、对象有限且容易验收的最小闭环。优先限定区域、对象类型、尺寸重量、运行时段、取放位置、任务下发方式和异常处理方式。明确列出 MVP 内、MVP 外与下一阶段候选，远期愿景不得混入首版承诺。

### 10. 编写验收标准

每项指标必须包含测试条件、样本量、计算口径和目标阈值。按场景选择任务完成率、单步成功率、作业时间、人工介入率、错放漏放、损坏跌落、安全距离、连续运行时长和故障恢复时间。阈值没有证据时标记 `待客户确认`，不得只写“准确率高”或“运行稳定”。

## 完成标准

- 已说明客户为何需要机器人，而不只是机器人要做什么。
- 已区分客户原话、确认事实、待验证假设和未知项，并为关键未知项安排验证方法。
- 已把抽象目标改写为可观察的环境状态，定义开始、完成、失败和停止条件。
- 已形成可回放的任务 SOP，并覆盖人员协作、安全、异常、重试和人工接管。
- MVP 构成端到端闭环，范围足够小，且明确列出暂不支持项。
- 验收标准可以在指定现场条件下重复测试，未确认阈值被显式标记。
- 未过早绑定技术实现，也未承诺未经 PoC 或工程评估验证的能力。
- `team-spec/active/{slug}/spec/discovery.md` 已创建或更新，并记录本轮 Change Log。

如果关键业务目标、目标状态、现场安全边界或 MVP 闭环仍未知，不要宣称需求发现完成；说明当前成熟度并继续引导。

## 最终回复

同步模式每轮回复保持短小，包含：

1. 本轮确认或修正了什么。
2. 当前最关键的决策点及其影响。
3. 一个核心问题、候选答案或验证建议。

异步模式每批输出包含：

1. 当前已知事实、待验证假设和本批目标的简短摘要。
2. 五到八个带稳定编号、必答/选答、提问原因和候选答案的问题；确有必要时最多十个。
3. 可复制的编号答复模板和需要附带的材料说明。
4. 收到答复后的批次复盘；部分回答不得被丢弃或要求整批重填。

需求发现达到完成标准或用户要求阶段性收口时，最终回复包含：

- 场景需求结论与当前成熟度。
- 已生成或更新的 `spec/discovery.md` 路径。
- 仍待确认的高影响问题和建议验证动作。
- 下一步有序选项，通常包括继续现场验证、进入 `team-spec-refine`，或暂停并保留当前发现结果。
