# PRD 交接评审

这个技能用于将 AI 结构化 PRD 转换为适合人类评审的交接文档，解决 AI-PRD 对产品、研发、项目管理三类受众都难以直接阅读和讨论的问题。它是规格阶段与工程阶段之间的正式门控——未完成交接评审，不应进入 `team-prd-to-issues`。

## 输入物

主输入：

- `team-spec/prd/{slug}.md`。

参考输入：

- `team-spec/spec/reviews/{slug}.md`：规格评审报告（风险和阻塞项）。
- `team-spec/spec/refine/{slug}.md`：规格细化产物（背景和用户诉求）。
- `team-spec/spec/CONTEXT.md`：长期共享上下文。

如果无法唯一确定 `{slug}`，应停止并要求用户提供，不得猜测。

## 输出物

- `team-spec/prd/{slug}-handoff.md`：人类可读的交接评审文档。

交接评审文档本身不修改 PRD 内容，只提供面向评审的视角呈现和签字记录。PRD 文件是工程实现的权威来源，交接文档是评审通过的证明。

## 交接文档结构

交接文档应面向三类受众，用自然语言而非机器字段组织内容：

### 产品侧关注

- 这个需求解决了什么用户问题？（一段话，避免专业术语）
- 用户会看到什么变化？（以用户视角描述）
- 验收口径是否准确反映了原始需求意图？（对照检查，不是逐条罗列）
- 哪些需求点在 PRD 固化过程中被调整或裁剪了？（需明确说明，不得隐藏）

### 研发侧关注

- 技术边界：明确说明实现范围，哪些不做。
- 依赖和前置条件：外部服务、数据、权限、基础设施。
- 已知技术风险和对应的缓解策略。
- 需要研发在评审中确认的假设（工作量、可行性、方案选型）。

### 项目管理侧关注

- 需求范围概述（用于排期估算）。
- 已知阻塞项和未决决策点（影响排期的）。
- 依赖其他团队或外部系统的事项。
- 建议的阶段划分（如有）。

### 待决事项

列出所有在评审前尚未确认的问题，每条注明：

- 问题描述。
- 影响范围（影响排期 / 影响范围 / 影响方案）。
- 期望决策人。

### 评审签字

```md
## 评审签字

| 角色         | 姓名 | 状态                  | 备注 | 日期 |
|--------------|------|-----------------------|------|------|
| 产品负责人   |      | ☐ 待评审 / ☑ 通过 / ✗ 拒绝 |      |      |
| 研发负责人   |      | ☐ 待评审 / ☑ 通过 / ✗ 拒绝 |      |      |
| 项目管理     |      | ☐ 待评审 / ☑ 通过 / ✗ 拒绝 |      |      |
```

三方均为"通过"后，方可执行 `team-prd-to-issues`。任一方"拒绝"或存在未决事项，应回到对应阶段处理。

## 工作流

1. 读取 PRD，提取核心目标、功能范围、验收标准、风险、假设。
2. 读取规格评审报告（如存在），补充风险和阻塞项。
3. 按三类受众分别生成对应章节，使用自然语言，避免机器格式字段。
4. 提取所有待决事项并单独列出。
5. 生成评审签字表（初始状态均为"待评审"）。
6. 将文档写入 `team-spec/prd/{slug}-handoff.md`。
7. 告知用户：请三方评审并填写签字表，完成后方可运行 `team-prd-to-issues`。

生成过程中如发现 PRD 存在逻辑矛盾、范围不清或验收标准缺失，应在"待决事项"中明确列出，不要试图自行填补。

## 写作原则

- **不重复 PRD**：不要把 PRD 的内容原样复制，要用评审者能直接理解的语言转述。
- **面向对话**：交接文档应能支撑一次评审会议，每个章节都要能在会上直接被讨论。
- **暴露分歧**：如果 PRD 内容与规格细化产物之间存在出入，必须在文档中明确标出，不要掩盖。
- **不替代人工决策**：待决事项必须留给人类决策，不要在文档中自行给出结论。

## 完成标准

- `team-spec/prd/{slug}-handoff.md` 已生成。
- 文档覆盖产品、研发、项目管理三类受众的关注点。
- 所有待决事项已单独列出。
- 评审签字表已生成，初始状态为"待评审"。
- 用户明确知道：签字完成前不应进入 `team-prd-to-issues`。
