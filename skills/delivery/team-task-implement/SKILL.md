# Task 实现

实现 `team-prd-to-tasks` 或 `team-tech-debt-to-tasks` 生成的一个 Task。所有同 slug Task 共用与 slug 完全同名的 `{slug}` 分支，不添加 `spec/` 前缀；每个 Task 验证通过后，必须先让用户检查实际差异并确认，再形成一个本地逻辑 commit。

## 触发边界

- 适合触发：用户指定一个明确 Task，要求实现、验证并在本地提交。
- 不适合触发：多个 Task 连续执行时使用 `team-task-batch-implement`；只审查现有实现时使用 `team-task-verify`；创建 PR/MR 时使用 Spec 级创建技能。

## 运行时配置

在读取 Task、代码或测试前，先读取 `team-spec/config.yml`。文件不存在或实现、提交所需字段缺失时，先使用 `team-config-init` 创建或增量补全；本技能不得自行回写配置。应用 `language`、`version_control`（含 `trunk_branch`、`contribution_model`、`source_remote`、`target_remote`）和 `access_policy`；缺少写权限或无法确定主干分支时停止。

Commit message 语言按“用户对本次提交的明确指定 > `version_control.language` > 顶层 `language` > `en-US`”确定。交付语言与 Task 文档语言不同时，只转换变更摘要，不修改 Task 原文；代码标识符和专有名词保持原样。Commit message 只写简洁的变更摘要，不添加 `T001` 等 Task ID 前缀或后缀。

默认 Spec 分支为 `{slug}`。用户显式指定且已确认的分支名可以覆盖默认值，但同一 slug 的所有 Task 必须使用同一个分支。

## 公共写作风格

生成或改写文档、用户可见说明或代码注释前，读取配置中的 `writing_style.guide`（如果存在）。格式、状态、安全、证据和验收合同优先。

## 输入物

主输入必须是唯一 Task：

- `team-spec/active/{slug}/tasks/T{nnn}-{short-task-slug}.md`
- 或用户显式指定的 Task 文件。

参考输入包括同 slug 的 PRD、规格、评审、上下文、决策、可选的 `design/functional-design.md`、代码、测试和 `./references/PLATFORM-STDLIB.md`。功能设计文件不存在时不阻塞实现；存在时不得绕过其中已确认的接口、数据、兼容或迁移约束。

必须确认：

- Task 有 `Task ID`、验收标准、类型和依赖。
- HITL 决策已完成。
- `Blocked by` 中所有 Task 已 `committed`。
- Task 尚未对应其他 commit。
- 当前工作区没有无法归因的变更。

无法唯一定位 Task 或 slug 时停止，不扫描 archive 猜测。

## 输出物

- 满足 Task 验收标准和当前受支持契约的代码与测试，包括必要的新增、修改或删除。
- `team-task-verify` 的独立验证结果。
- 用户检查差异并明确确认后创建的一个本地逻辑 commit。
- 等待确认时 Task 文件中的 `Status: verified`；提交后更新为 `Status: committed`，并记录 commit SHA、实现和验证结果。

不得 push、创建远端 Issue、PR 或 MR。`team-spec/` 下的运行时文件不得加入代码 commit。

## 共享分支合同

1. 从 `team-spec/config.yml` 确定 `trunk_branch`、`contribution_model`、`source_remote` 和 `target_remote`。
2. 将 Spec 分支计算为 `{slug}`，不得添加 `spec/` 或其他前缀。
3. 当前分支不是 Spec 分支时：
   - 工作区有未提交变更则停止。
   - 分支已存在：切换到该分支，不执行主干同步。
   - 分支不存在：先同步主干，再从主干创建。
4. 同步主干规则（仅在创建新分支时执行）：
   - `contribution_model = direct`（source_remote 与 target_remote 相同）：`git switch {trunk_branch}`，然后 `git fetch {source_remote} {trunk_branch}`，再执行 `git pull --ff-only {source_remote} {trunk_branch}`。切换主干前必须确认工作区干净；无法 fast-forward 时停止，不自动 merge 或 rebase。
   - `contribution_model = fork-pull`（target_remote 为上游仓库）：`git fetch {target_remote} {trunk_branch}` 然后 `git switch {trunk_branch}` 然后 `git merge {target_remote}/{trunk_branch}`。
   - 同步后，`git switch -c {slug} {trunk_branch}` 创建新分支。
5. 后续 Task 必须继续使用同一分支。
6. 不创建 Task 独立分支，不把其他 slug 的 commit 混入当前分支。

## 最小实现模式

实现前写出真实入口、已有实现、最小修改路径、可复用能力、拒绝的复杂方案和验证命令。

涉及 URL、日期、CSV、分页、路径、CLI、数据库约束或 UI 原生控件时，读取 `./references/PLATFORM-STDLIB.md` 后再决定实现。

不得以最小实现为由删除权限、输入校验、错误处理、事务、幂等、迁移兼容、可访问性或用户明确要求。

## 工作流

1. 读取配置、Task、PRD 和必要上下文。
2. 校验依赖、工作区和 Spec 分支；创建或切换到共享分支。
3. 将本地 Task 状态更新为 `implementing`。
4. 输出最小路径检查、测试设计、契约变更分类和 commit 范围预览。
5. 按行为 TDD 执行 red-green-refactor。
6. 运行新增或修改的测试、Task 相关测试和受影响的回归测试。
7. 自动衔接 `team-task-verify`，不在验证前提交。
8. 验证不是 `verified` 时停止，不创建 commit。
9. 验证通过后、暂存任何文件之前，生成提交前检查摘要并进入“提交前确认”。
10. 用户选择继续修改时，完成修改、重新运行受影响验证并再次生成检查摘要；旧确认立即失效。
11. 只有用户明确选择“接受当前实现并提交”后，才暂存本 Task 的代码、测试和必要配置；排除 `team-spec/` 和无关改动。
12. 创建一个逻辑 commit，推荐信息为 `{concise localized change summary}`，例如 `Add filtered export support`；不得添加 Task ID，标题使用已确定的版本控制交付语言。
13. 确认 commit 已创建且工作区没有遗留的本 Task 代码变更。
14. 回写 Task：`Status: committed`、`Commit: {sha}`、实现、验证命令和残余风险；不得暂存该回写。

## TDD 循环

```text
RED：写一个行为测试并确认失败
GREEN：写最小实现让测试通过
REFACTOR：相关测试通过后再整理结构
```

RED 必须记录执行命令、预期缺失的行为和实际失败原因。接口签名或类型契约变化导致的预期编译、类型检查失败可以作为有效 RED；与目标行为无关的环境、导入、fixture 或基础设施失败不算 RED。

## 测试行为，不测试实现

测试应证明业务规则或公共契约。先用不包含内部类名、私有方法名和调用链的语言描述“给定什么条件、执行什么操作、应观察到什么结果”，再编写测试。默认以 E2E 为主，从产品实际用户入口走到用户可见结果；用户入口可以是 UI、CLI 或供调用方使用的 API，不能为缩短路径绕过正在验收的用户入口。

- 断言返回结果、业务状态变化、持久化结果或对外可观察的副作用；不得把私有方法、内部字段、对象拆分、内部调用顺序或次数当作验收结果。不要为了测试暴露私有实现，也不要逐个生产方法机械生成对应测试。
- 区分内部调用与业务效果：调用次数不能直接证明结果是否正确、缺失或重复。通过公共入口触发行为，并观察契约规定的结果；允许不同实现使用不同内部调用路径达成同一结果。
- 保留被测业务逻辑真实执行，禁止 Mock；依赖替代和时间控制必须遵守“真实依赖、Fake 与时间控制”，不得用预设返回值证明成功。
- 只有交互本身属于明确的对外契约时，才能断言交互内容、顺序或次数，并注明契约依据；例如对外发布的事件及其业务字段。内部方法调用次数不因容易观测就成为业务契约。
- 写完后做重构敏感性审查：如果只重命名私有方法、拆分或合并内部类、更换等价算法、调整内部调用链，公共行为不变，测试是否仍成立？会因此失败的测试应改写到稳定边界；不得为维持这类测试冻结实现结构。审查即可，不要求为证明这一点额外执行无关重构。
- 纯重构应复用既有行为测试证明行为保持。若必须批量修改断言、Mock 或快照，先检查是否绑定了实现细节；必要的装配调整可以修改，但不得悄悄改变业务预期或把内部结构变化称为契约替换。

## 测试命名

- 测试名称统一表达“条件或操作 + 可观察结果”；存在影响结果的前置条件时必须写明，使失败报告不打开测试代码也能说明哪条行为未满足。名称必须与实际断言一致，不能只写“正常”“成功”“异常”而省略具体结果。
- 用户交互类测试从用户行为描述，系统触发类测试从事件或条件描述。使用领域术语或公共契约术语，不以私有方法名、内部调用链或调用次数命名。
- 测试函数标识符遵循项目语言和框架约定，显示描述遵循项目写作风格；框架要求的 `test_` 等前缀可以保留，但后续必须表达行为。分组标题与用例名可以共同组成完整描述，避免逐层重复；参数化用例应提供可区分场景的标签，不能仅靠序号定位失败。
- 将规则用于新增和本次修改的测试，不为统一名称批量重命名无关用例；如名称被测试选择器引用，同步更新相关选择配置，避免选测遗漏。

## 真实依赖、Fake 与时间控制

- 禁止使用 Mock，包括动态替换业务方法、预设调用返回值、交互期望和调用次数验证；不得将这些做法改名为 Fake 或 Spy 规避规则。既有受本次改动影响的 Mock 测试应改写为真实行为测试，不要求顺带清理无关测试。
- Redis、PostgreSQL 等可在测试环境运行的基础设施优先使用真实实例，通过容器或项目现有测试服务提供，隔离测试数据并清理。不得仅因 Fake 编写方便就替换真实存储引擎；内存替代不能证明真实系统的查询、事务、约束或过期语义。
- 外部系统确实难以接入时，才通过明确的依赖接口注入 Fake，并记录原因及替代边界。Fake 是具有实际行为的简化实现，按输入和状态执行必要规则；不得只按预设调用顺序返回答案，不得替代产品内部被测逻辑。
- Fake 必须与真实系统校验契约：尽可能将同一组契约用例分别运行于 Fake 和真实系统或其官方测试环境，核对本项目依赖的请求、响应、错误和状态语义。记录真实侧版本、执行结果和覆盖限制；仅按接口文档编写 Fake 或验证 Fake 自身不算完成校验。无法接入真实侧时明确缺失证据，相关关键验收不得标为已通过。
- 外部契约验证按依赖变更和定期完整测试安排执行，可复用版本匹配且可追溯的证据，不要求每次本地 E2E 连接真实外部系统。Fake、适配器或真实依赖契约变化后，重跑受影响的契约用例。
- 时间逻辑使用可控时钟和 fake timer，显式推进时间、触发到期任务并断言可见结果；禁止用固定 sleep 等待超时、重试或过期后再断言。fake timer 是允许的时间控制工具，不用于替换业务方法。
- 跨进程或真实基础设施的时钟不受进程内 fake timer 控制，不得声称推进本地时间就覆盖了真实系统的时间语义。此类验证使用系统支持的时间控制；无法控制时，以有截止时间的条件等待、事件或状态探测同步，超时给出诊断，不能用固定 sleep 猜测完成。

## E2E 优先与分级执行

- 大部分行为覆盖优先写 E2E，保留产品内部链路真实执行，优先接入真实基础设施；难以接入的外部系统按上述规则注入经过契约校验的 Fake。不得把绕过用户入口的内部方法测试称为 E2E，也不要求每次连接全部真实外部服务。
- 只有 E2E 不适合证明目标行为时，再选择契约、集成或单元测试，并说明具体原因，例如难以稳定触发的故障、组合繁多的算法边界或真实外部协议语义。其他层级仍测试公共行为；不设固定比例，不为凑测试金字塔在各层重复覆盖。
- 测试规模增长后，按反馈成本和运行时机分为快速冒烟、按影响选择的回归、完整测试集；执行分级与 E2E/集成/单元的类型划分独立，快速 E2E 也可进入冒烟。优先使用项目已有的标签、测试清单和依赖图，不为小规模测试集另建复杂平台。
- 本地迭代先运行当前行为的定向测试；Task 验证和 PR CI 运行快速冒烟、新增或修改的测试，以及根据实际 diff 和依赖关系选出的受影响回归。选择范围应包含间接依赖的用户链路、共享配置、数据格式、fixture 和 Fake；不能只按同名文件或修改行数选测试。记录选择依据、命令和未覆盖风险。
- 依赖映射不可靠或公共基础设施、跨模块契约变更影响广泛时，扩大到相关测试组，必要时全量运行。不得为了缩短 CI 跳过已知受影响的测试，也不得默认每个小改动都跑完整测试集。
- 完整测试集按项目明确的周期运行，并在发布前按发布规则运行；优先沿用已有 CI 调度。没有周期时，在验证说明中明确建议周期及尚未落地的状态，不把计划当成已执行证据。定期全量发现漏选时，修正影响映射并补跑受影响测试。
- 同一代码、配置及依赖状态已有可追溯的通过结果时，实现与验证阶段可复用执行证据，验证阶段仍需独立审查断言和选测范围；相关输入变化、证据不完整或出现新风险时重跑，避免无依据地重复执行耗时测试。

## 测试规则自动检查

- 将可稳定机械判定的测试规则固化为目标项目的 lint、静态检查或 CI 检查，优先复用已有工具，并接入日常快速验证入口。根据项目语言和框架检查禁止的 Mock API、用于猜测完成的固定 sleep、测试标识符格式等；区分允许的 fake timer 和有截止时间的条件等待，避免仅凭关键词误报。
- 测试分级、定期全量调度和选测映射由配置或工作流检查验证；Fake 与真实系统的一致性由契约测试验证。业务描述是否清楚、断言是否有效、测试是否耦合实现细节保留语义审查，不以 lint 通过代替行为验收。
- 新增或修改自动检查时，用违规与合法样例验证能检出问题且不会误伤，说明检测范围和限制。仅补充当前改动需要的检查，不为覆盖所有规则另建通用检查平台；不能可靠自动判定的规则明确保留审查方式。

## 测试设计与契约维护

测试是当前受支持契约的可执行说明，不是历史行为档案，也不是只增不减的记录。Task 验收标准、父 PRD、功能设计和明确的兼容决策高于既有测试；既有测试只是实现证据。两者冲突且上游意图不明确时停止确认，不得仅因旧测试存在就保留旧行为。

写测试前必须：

- 将每条验收标准映射到场景、用户入口和可观察断言，默认采用 E2E，不适合时说明其他测试层级的选择依据；按真实风险覆盖正常、错误、边界、权限、兼容和回归场景，不设固定用例数量。
- 将受影响的接口、参数、数据格式、配置项或命令行契约分类为“保持”“替换”或“兼容迁移”，并指出判断依据。
- 查找受影响的既有测试、fixture、Fake/Mock、快照和示例，决定修改、删除或基于明确兼容要求保留；优先改写最接近当前行为的测试，不为同一行为机械追加重复用例。

契约被替换时：

- 同一 Task 内修改或删除只描述旧契约的测试及辅助数据。测试数量可以下降；删除失效测试是正确维护，不是覆盖率退化。
- 旧参数或旧行为只有在 PRD、设计、验收标准或用户明确要求向后兼容、迁移过渡或稳定拒绝行为时才能保留测试；记录依据和移除条件。没有依据时不得生成“旧参数检查”测试。
- 编译器或类型系统已经保证旧源码参数不可用时，不再写运行时测试重复证明。只有旧值来自动态外部输入，且拒绝方式属于稳定公共契约时，才测试错误码等可观察结果。

每个新增或修改的测试还必须满足：

- 优先走从用户入口到可见结果的真实路径；禁止 Mock，Fake 仅用于难以接入的外部依赖，时间使用 fake timer，随机性通过可注入的确定性来源控制，不截断被测内部业务链路。对外交互契约通过边界可观察结果验证，不通过内部调用次数验证。
- 预期值独立于生产实现生成，不复制被测算法，不使用无断言、恒真断言或只证明 fixture/Mock 自己行为的用例。
- 能在至少一个合理的错误实现下失败，例如忽略新参数、错误接受旧参数、绕过权限或固定返回成功；不要在多个测试层级重复同一证明。
- 对未覆盖但与本次变更相关的风险说明原因，并运行足以发现受影响旧行为回归的测试范围。

## 提交前确认

验证通过后、暂存任何文件之前，必须暂停自动流程，让用户有机会在本地检查实际代码差异。不得先执行 `git add`，否则普通 `git diff` 无法直接展示待提交变化。

先向用户提供：

- 当前 Task、分支和验证状态。
- 修改、新增及删除文件清单、测试的新增/改写/删除摘要、保留的兼容测试依据、`git diff --stat` 摘要和拟提交范围。
- 已运行的验证命令、结果、跳过项和残余风险。
- 可在本地使用的检查入口：`git status --short`、`git diff --stat` 和 `git diff`。这些命令只写在用户可复制的说明中，不添加环境专用执行包装器。

然后给出以下选择并等待用户明确回复：

1. `✅ 接受当前实现并提交`：按已展示范围暂存并创建本地 commit。
2. `🔍 暂不提交，我要先查看 diff`：保持所有实现未暂存、未提交，等待用户检查后再次决定。
3. `🔄 继续修改当前 Task`：询问或读取修改意见，修改并重新验证，再回到本确认节点。
4. `⏸️ 暂停并保留当前改动`：停止本轮，不提交、不回滚，保持 `Status: verified` 和当前工作区。

不得把用户在任务开始时说的“实现并提交”、AFK 授权或批量执行授权视为这次提交确认。确认只对当前已展示的 Task、文件范围和实际 diff 有效；确认后只要代码、测试或必要配置再次变化，就必须重新验证并再次确认。

提交前确认是代码交付控制点，不是产品或技术方案决策，不改变 Task 原有的 AFK/HITL 分类。

## Commit 合同

- 一个 Task 对应一个最终逻辑 commit。
- commit 只能在 Task 验证通过后创建。
- commit 只能在用户查看提交前摘要并明确确认当前实际 diff 后创建。
- commit 范围必须与 Task 验收标准一致。
- commit message 使用简洁的祈使句或变更摘要，不包含 `T001` 等 Task ID；Task 与 commit 的关联只通过 Task 文件中的 `Commit: {sha}` 和后续 Task/commit 映射维护。
- 不提交 `team-spec/`、无关格式化、顺手重构或其他 Task 的提前实现。
- 若实现无法安全形成一个 commit，应停止并回到拆解技能调整边界。
- 创建 commit 不代表允许 push；远端操作只由 Spec 级技能执行。

## 完成标准

- 当前分支是该 slug 的 Spec 共享分支。
- Task 的所有验收标准通过独立验证。
- 测试集合只描述当前支持的契约；旧契约引用已删除，或有明确的兼容依据和移除条件。
- 用户已基于当前实际 diff 明确确认提交。
- 已创建且只创建一个对应逻辑 commit。
- Task 文件记录 `committed` 和有效 commit SHA；如果用户选择查看、继续修改或暂停，则保持 `verified`，不得伪装为完成。
- 没有 push、远端 Issue、PR 或 MR。
- `team-spec/` 回写保持未暂存。

## 最终回复

必须包含：

- Task 路径、ID、slug 和共享分支。
- 主要代码变化，以及新增、改写、删除的测试和保留兼容测试的依据。
- 验收覆盖、验证命令和结果。
- 提交前确认结果；已提交时包含 commit SHA、commit 信息和范围，未提交时明确说明当前改动仍可用 `git diff` 检查。
- 未提交的 `team-spec/` 回写。
- 跳过项、残余风险和下一步。
