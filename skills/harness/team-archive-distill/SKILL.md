# 归档决策规则提取

这个技能以 `team-spec/CONTEXT.md` 为首要沉淀依据，结合指定归档提取决策模式和工程惯例，抽象为可复用规则写入 `team-spec/CONTEXT.md`。上下文与归档描述冲突时，列出冲突并建议以 `CONTEXT.md` 为准，不自动裁决。它不是项目文档生成器，也不是架构说明书。

本技能独立使用，不依赖产品需求链路（prd-to-tasks、task-implement 等），也不属于主线交付流程。

## 触发边界

- 适合触发：用户要从已归档的 spec 中提炼规则、更新 team-spec/CONTEXT.md 中的决策约束、复盘历史需求并沉淀惯例。
- 不适合触发：用户要维护代码级 harness（入口约束、失败记忆、验证策略、任务入口）时，这不属于本技能范围；用户要细化新需求、评审规格、生成 PRD 或拆 Task 时，转交对应产品/交付技能。

## 职责边界

本技能以已确认的上下文为首要依据、指定归档为补充证据，提取可复用规则并写入 `team-spec/CONTEXT.md`。

优先沉淀产品术语、角色、通用流程和业务规则；具有跨需求适用证据的工程规则也可以沉淀：

1. 架构规则：模块边界、技术选型约束、分层原则、依赖方向。
2. API/接口规则：命名惯例、版本策略、错误处理模式、向后兼容约束。
3. 数据规则：数据模型惯例、存储选择、迁移策略、schema 变更约束。
4. 测试规则：测试分层、覆盖率要求、验证策略、哪些变更必须跑哪些测试。
5. 流程规则：分支策略、代码评审要求、发布流程、部署约束。
6. 约束规则：已知不可触碰的边界、技术债务禁区、性能/安全红线。

本技能不负责：

- 维护 Codex 运行时检索层（入口约束、失败记忆、验证 harness、任务入口）。
- 写 PRD、拆 Task、实现 Task、验证 Task，或创建 Spec 级远端 Issue/PR/MR。
- 生成完整架构说明书或项目文档。
- 凭空编造规则；所有规则必须有上下文或指定归档中的证据支撑，不得将一次性需求选择扩大为全项目约束。
- 修改 `team-spec/archive/` 中的任何文件。

## 输入物

- 目标项目的 `team-spec/CONTEXT.md`（如存在）：首要沉淀依据，读取其中已确认的术语、角色、通用流程和业务规则。
- 用户明确指定的一个或多个归档 slug，或 `team-spec/archive/{slug}/` 下的具体文件路径。只读取被指定的归档范围，不默认枚举或扫描整个 `team-spec/archive/`。
- 被指定归档 slug 的以下产物（如存在）：
  - `spec/CONTEXT.md`：该需求的局部上下文，仅在该需求适用范围内作为首要依据。
  - `spec/refine.md`：细化过程中确认的需求和决策。
  - `spec/reviews.md`：评审中发现的风险、约束和修正。
  - `prd/prd.md`：固化的功能边界、验收标准和工程约束。
  - `design/functional-design.md`：架构设计决策和模块划分。
  - `DELIVERY.md`：交付过程中的经验教训和实际遇到的问题。
  - `ARCHIVE.md`：归档原因和生命周期总结。

如果用户没有明确指定归档 slug 或文件路径，停止并要求用户提供，不得通过扫描 archive 猜测范围。如果指定范围不存在或为空，停止并说明没有可提取内容。

## 输出物

- 新建或更新的 `team-spec/CONTEXT.md`：合并跨需求有效的术语、角色、通用流程、业务规则和工程约束，保留既有内容与组织结构。供需求细化、评审、PRD、任务拆解和后续研发读取。
- 用户可见的冲突清单：双方描述、来源位置、适用范围，以及建议以 `CONTEXT.md` 为准的理由。无冲突时明确说明。

只写入全局 `team-spec/CONTEXT.md`，不修改 `AGENTS.md`、局部上下文或归档内容。冲突清单在回复中展示，不将待确认结论写成有效规则。

## 规则写法

每条规则必须是高度抽象的、可复用的判断依据，而不是原始决策的复述。规则格式：

```markdown
#### {rule-title}

- 规则：{用一句话描述，Codex 在什么情况下应该遵守什么}
- 原因：{为什么这条规则是必要的，过去什么决策/问题导致了它}
- 例外：{什么情况下可以不遵守，如果没有则写 无}
- 来源：{引用归档 slug、文件及章节；保留既有条目的来源，不以输出文件自身作为新增结论的唯一证据}
- 最后更新：{YYYY-MM-DD}
```

规则必须满足：

- 抽象：保留适用条件；一次需求选用 PostgreSQL 不能直接推导为全项目默认选型。
- 可操作：Codex 读到后能直接用于决策。
- 有证据：新增或实质修改的结论必须引用指定归档中的具体证据；既有上下文保留原有来源，不要求补造归档证据。
- 已确认：归档不等于所有内容已生效。核对评审、交付和归档结论，排除未确认假设、已否决或已撤销方案；暂停或废弃需求只能贡献其中明确仍有效的结论。
- 不重复：同一事实只写在一个规则里。

## 规则分类

优先合并到现有全局上下文的语言、角色、流程、业务规则等对应章节，不复制已有内容。工程规则可在 `## 工程约束` 下按需分类：

1. `### 架构规则`：模块边界、技术选型、分层原则、依赖方向。
2. `### API/接口规则`：命名惯例、版本策略、错误处理、向后兼容。
3. `### 数据规则`：数据模型、存储选择、migration 策略。
4. `### 测试规则`：测试分层、覆盖率要求、验证策略。
5. `### 流程规则`：分支策略、评审要求、发布流程。
6. `### 约束规则`：不可触碰的边界、技术债务禁区、性能/安全红线。

如果某类规则暂无证据支撑，不创建空分类。术语和角色可用简短定义并附来源、适用范围，无需强套工程规则格式。

## 依据优先级与冲突处理

- 优先读取全局 `team-spec/CONTEXT.md`，再读取指定归档范围内的局部 `spec/CONTEXT.md`，最后对照其他归档产物。只指定具体文件时，不自动扩大归档读取范围。
- 全局上下文用于跨需求规则；局部上下文只解释对应需求。局部限定与全局规则能同时成立时不视为冲突，不将局部约定提升为全局默认。
- 上下文未覆盖的事项可以从指定归档补充，但必须有明确的可复用依据，不能仅凭某次选型推导全项目默认。
- 上下文与归档对同一适用范围的同一事项描述不一致时，逐项列出事项、双方描述及路径/章节、影响范围，以及“建议以 CONTEXT.md 为准”的理由。局部上下文与全局上下文本身冲突时也列出，建议以全局上下文为准。
- 优先级用于提出建议，不等于用户已确认冲突解决方案。冲突规则暂不新增、覆盖或删除；其余无冲突规则继续处理。不得为消除冲突自动改写既有全局结论，也不得修改归档。
- 全局 `CONTEXT.md` 缺失时，存在无冲突且证据充分的全局结论时才创建；没有可沉淀内容则不创建空文件。局部上下文缺失时使用其他指定归档证据，不补建局部文件。

## 工作流

1. 确认用户明确指定的归档 slug 或文件路径，并拒绝自动扩大到其他归档。
2. 应用运行时配置和访问策略，读取全局上下文、指定范围内的局部上下文与其他归档产物。
3. 从上下文识别已确认且可复用的判断依据，再从归档补充决策、约束和经验。
4. 按“依据优先级与冲突处理”核对适用范围并列出冲突；将无冲突的相似规则归并，消除重复。
5. 区分产品语境与工程约束，为新增或修改条目标注归档来源、适用范围，排除未确认或已失效内容。
6. 将无冲突条目合并到全局 `team-spec/CONTEXT.md` 对应章节，保留已有内容和来源；文件不存在时按实际内容创建。重复执行时不重复追加相同条目。
7. 没有可提取规则时说明原因，不强行写入；全部候选项均有冲突时，仅输出冲突清单。
8. 自检：每条规则是否保留上下文的适用范围、抽象、可操作、有证据、不重复。

## 汇总粒度

- 单条规则可以来自上下文与多个指定归档的共同证据。
- 同一归档 slug 可以贡献多条不同类型的规则。
- 如果候选规则与现有 `team-spec/CONTEXT.md` 规则冲突，标注为待确认，不自动覆盖。
- 归档日期较新不代表它可以推翻 `CONTEXT.md`。归档间存在分歧时先核对上下文；上下文未覆盖或证据不足时列为待确认，不按时间自动裁决。
- 只有证据明确且不存在待确认冲突时，才可更新已失效的历史规则。

## 运行时配置

本技能读取目标项目根目录下的 `team-spec/config.yml` 作为运行时配置入口，主要用于获取 `writing_style.guide` 路径。

如果 `team-spec/config.yml` 不存在或缺少本轮需要的字段，先使用 `team-config-init` 创建或增量补全。本技能不得自行创建或回写配置；纯对话和只读分析可以继续，但写入 `team-spec/CONTEXT.md` 前必须完成所需配置。

如果配置存在 `access_policy`，读取上下文、指定 archive 内容和写入 `team-spec/CONTEXT.md` 前都必须先应用对应目录边界。访问策略不能被“只读提炼”或用户笼统要求扫描历史记录所绕过。

语言优先级为：用户本轮明确指定 > 配置中的 `language` > 目标 `team-spec/CONTEXT.md` 的既有主要语言。

## 公共写作风格

生成或改写 `team-spec/CONTEXT.md` 前，检查 `team-spec/config.yml` 中的 `writing_style.guide`。该路径指向存在的文件时，写作前必须读取并应用；相对路径以目标项目根目录解析。

优先满足格式、状态、安全、证据和验收合同，再按“用户本轮要求 > 本技能的产物类型规则 > 项目风格指南 > 目标文件相邻内容”处理表达。指南缺失时继续使用本技能规则，不阻塞任务、不猜测路径；需要建立或调整统一风格时使用 `team-writing-style`。

## 自检要求

每次更新 `team-spec/CONTEXT.md` 后，必须轻量自检：

- 条目是否属于跨需求有效的产品语境或工程约束，是否保留既有组织结构。
- 每条规则是否抽象、可操作；新增或实质修改的结论是否引用指定归档证据，既有条目是否保留原有来源。
- 是否存在重复规则，或同一事实分散在多个规则中。
- 是否引用了不存在的上下文位置或归档来源。
- 是否列全上下文与归档的冲突并建议以上下文为准，且没有将待确认项写成有效规则。
- 是否仅写入全局 `team-spec/CONTEXT.md`，未修改 `AGENTS.md` 或归档文件。
- 是否需要降级、删除或标注被后续归档推翻的旧规则。

## 与其他技能的关系

- `team-spec-archive`：将 active 需求归档到 archive。本技能读取其产物。
- `team-writing-style`：建立或调整统一写作风格。本技能在生成 `team-spec/CONTEXT.md` 规则时应用其风格指南。
- `team-spec-refine`、`team-tech-debt-refine`：只读全局上下文，在当前需求内记录候选内容和局部语境；归档后由本技能评估并沉淀到全局上下文。
- 本技能独立运行，不是产品交付链路的必经步骤；沉淀到 `team-spec/CONTEXT.md` 的规则供后续任务使用。

## 完成标准

- 存在无冲突的可复用规则时，已更新 `team-spec/CONTEXT.md` 对应章节；无可写入规则时，已说明原因。
- 每条规则抽象、可操作、有证据、不重复。
- 没有编造规则；新增或实质修改的结论可追溯到指定归档，既有条目保留原有来源。
- 只写入全局上下文，未修改 `AGENTS.md` 或归档；冲突项已列出并建议以既有 `CONTEXT.md` 为准，未自动裁决。
- 规则分类清晰，没有空分类。

## 最终回复

必须包含：

- 实际读取的上下文路径，以及指定归档 slug 数量和列表；缺失的上下文。
- 每个 slug 中提取到的决策/模式数量。
- 全局上下文路径，以及新增、更新、保留和待确认条目的数量与摘要。
- 每条规则的摘要和具体来源。
- 未提取到规则的 slug 及原因。
- 待确认的冲突清单：双方描述、来源位置、适用范围、建议及理由；无冲突时明确说明。
