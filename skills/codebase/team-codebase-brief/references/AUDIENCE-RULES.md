# 受众表达规则

## 目录

- 1. 通用规则
- 2. 产品受众
- 3. 业务/运营受众
- 4. 管理层受众
- 5. 客户相关受众
- 6. 技术细节降级

## 1. 通用规则

- 先讲业务场景，再讲系统能力，最后讲边界和风险。
- 用“谁、在什么情况下、要完成什么、系统如何支持、有什么限制”组织表达。
- 技术事实要可追溯，但不要把代码细节放到主要叙述中。
- 所有不确定项都转成可决策问题。

## 2. 产品受众

产品更关心：

- 当前能力边界。
- 用户场景和体验影响。
- 可配置项和可运营策略。
- 改造成本线索。
- 需要产品决策的问题。

避免只说“接口支持/不支持”。要翻译成“用户是否能做某件事”。

## 3. 业务/运营受众

业务和运营更关心：

- 流程是否可执行。
- 是否需要人工介入。
- 异常情况怎么影响用户或团队。
- 数据口径和可见性。
- 上线或变更后工作方式变化。

避免讲内部模块名。用流程节点和运营动作表达。

## 4. 管理层受众

管理层更关心：

- 能力现状。
- 对交付、成本、风险、路线图的影响。
- 关键依赖。
- 决策项和优先级。

材料要短，避免细节堆砌。每个风险都要带影响和建议动作。

## 5. 客户相关受众

售前、客户成功或外部沟通更关心：

- 能力能承诺到什么程度。
- 哪些场景已支持。
- 哪些场景需要定制或暂不支持。
- 风险和限制如何表达。

避免泄露内部实现、敏感配置、源码路径和未公开技术债。

## 6. 技术细节降级

| 技术表达 | 面向业务/产品的表达 |
| --- | --- |
| 函数/类 | 能力步骤或系统动作 |
| 调用栈 | 业务流程或系统流转 |
| 数据表/字段 | 业务对象、状态或指标 |
| 配置项 | 策略开关、环境约束或运营参数 |
| 测试缺口 | 待验证风险 |
| 代码耦合 | 改造影响面或联动成本 |
| 外部服务依赖 | 业务链路依赖 |
