# 代码库业务简报工作流

## 目录

- 1. 目标与边界
- 2. 阶段一：确认来源、受众和目标
- 3. 阶段二：提取可分享事实
- 4. 阶段三：业务能力映射
- 5. 阶段四：场景化表达
- 6. 阶段五：风险、边界和决策问题
- 7. 阶段六：成文与校验
- 8. 证据不足处理
- 9. 最终回复

## 1. 目标与边界

本技能不是重新分析全量代码库，也不是替代 `team-codebase-onboarding` 或 `team-codebase-walk`。它负责把已有技术事实和人类指定来源转成非技术干系人可理解的分享材料。

默认只写：

```text
team-spec/active/{slug}/brief/codebase-brief/
```

不得修改业务源码、测试、构建配置、部署配置、迁移脚本、onboarding 产物或 walk 产物。

## 2. 阶段一：确认来源、受众和目标

先确定：

- slug 或明确输出路径。
- 用户指定的数据来源。
- 目标受众：业务、产品、运营、管理层、售前、客户成功、合规或混合受众。
- 分享目标：能力介绍、场景讲解、改造影响、风险说明、路线图对齐、决策预读或会议大纲。
- 期望形式：简报、场景 walkthrough、FAQ、会议大纲或完整文档集。

来源规则：

- 用户指定来源优先级最高。
- 如果用户指定来源，只围绕这些来源展开，除非为解释结论必须补少量证据。
- 如果用户未指定来源，默认读取：
  - `team-spec/active/{slug}/design/codebase-onboarding/`
  - `team-spec/active/{slug}/design/codebase-walk/`
- 如果默认来源不存在，读取 README、docs、PRD、ROADMAP 或源码做最小补证据，并建议先运行上游技能。

## 3. 阶段二：提取可分享事实

从来源中提取：

- 系统支持的业务能力。
- 用户、调用方、运营方或外部系统。
- 关键触发场景和业务流程。
- 能力边界：支持什么、不支持什么、需要什么前置条件。
- 产品影响：体验、效率、自动化、数据可见性、交付速度、运营成本。
- 风险和约束：数据、合规、稳定性、性能、依赖、测试缺口、技术债。
- 需要业务/产品确认的问题。

不要把技术细节直接搬进材料。源码路径、函数名、类名和调用栈只作为证据，不作为主要叙述。

## 4. 阶段三：业务能力映射

把技术事实映射成业务表达：

| 技术事实 | 业务表达 |
| --- | --- |
| API / handler / job | 一个用户动作、系统事件或后台能力 |
| 数据模型 / schema | 业务对象、状态或指标口径 |
| 配置 / feature flag | 能力开关、运营策略或环境约束 |
| 外部依赖 | 业务链路依赖或服务风险 |
| 测试缺口 / TODO | 交付风险或待验证假设 |
| 高变更文件 / 高耦合模块 | 变更成本或联动风险 |

每个能力建议包含：

- 能力名称。
- 业务场景。
- 受众或使用者。
- 当前边界。
- 证据来源。
- 产品或交付影响。

## 5. 阶段四：场景化表达

优先用“场景 -> 系统能力 -> 业务价值 -> 边界/风险 -> 需要确认的问题”的顺序讲述。

场景说明要回答：

- 谁在什么情况下触发这个能力。
- 系统帮他完成什么。
- 成功后业务上发生什么变化。
- 失败或边界情况会影响谁。
- 产品或运营需要知道什么。

避免：

- 从代码文件开始讲。
- 逐函数解释。
- 让非技术受众理解内部调用栈。
- 用技术缩写代替业务场景。

## 6. 阶段五：风险、边界和决策问题

风险要按非技术影响表达：

- 体验风险：用户是否会感知。
- 运营风险：是否增加人工介入或流程复杂度。
- 数据风险：口径、完整性、权限、隐私或合规。
- 交付风险：改动范围、依赖、测试缺口和回归成本。
- 商业风险：影响客户承诺、路线图或上线节奏。

需要确认的问题要写成业务/产品能回答的问题，而不是技术 TODO。

示例：

- 不写：“需要确认 `FooService` 的状态分支。”
- 写：“需要产品确认订单取消后是否仍允许重新触发该能力。”

## 7. 阶段六：成文与校验

写文档前读取 `OUTPUT-SPEC.md` 和 `AUDIENCE-RULES.md`。

按分享目标选择文档：

- 总览分享：`executive-summary.md`、`alignment-outline.md`。
- 能力梳理：`business-capability-map.md`。
- 场景讲解：`scenario-walkthrough.md`。
- 产品规划：`product-impact.md`、`risk-and-constraints.md`。
- 会前准备：`stakeholder-qa.md`、`alignment-outline.md`。

## 8. 证据不足处理

按以下顺序处理：

1. 检查用户指定来源。
2. 检查 onboarding 和 walk 产物。
3. 检查 README、docs、PRD、ROADMAP、ADR。
4. 必要时读取少量源码或配置作为证据。
5. 仍不足时写 `[TODO]`。
6. 需要业务判断时写 `[ASK USER]`。

不要为了让材料完整而编造业务价值、用户场景或产品影响。

## 9. 最终回复

最终回复使用中文，并包含：

- 本次使用的数据来源。
- 目标受众和分享目标。
- 创建/更新的材料。
- 关键业务能力和风险摘要。
- 需要业务/产品确认的问题。
