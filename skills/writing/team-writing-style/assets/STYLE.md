# 团队写作风格

这份指南约束项目中的中文文档、用户可见说明和代码注释。目标是让内容准确、直接、像熟悉业务和代码的人写成，同时保留不同文档类型应有的结构。

## 约束优先级

先满足产物格式、机器状态、安全、证据和验收合同，再处理文风。发生冲突时，按以下顺序判断：

1. 产物的格式、状态、安全和证据合同。
2. 用户本轮明确提出的要求。
3. 当前技能针对 PRD、README、评审材料或代码注释的补充规则。
4. 本指南。
5. 目标文件相邻内容的既有写法。

风格调整不能改变事实、数字、状态值、字段名、验收标准和引用含义。

## 通用表达

- 先写结论、事实或变化，再补原因和背景。
- 写清楚主体、动作、对象和结果。能写“审批失败后保留已填写内容，并提供重试入口”，就不要写“全面提升流程体验”。
- 删除不承载信息的开场、过渡和总结，例如“下面我们来看”“值得注意的是”“综上所述”。
- 少用只表达态度的词。出现“重要”“高效”“智能”“全面”“显著”“赋能”时，检查它是否带来可验证信息；没有就删除或改写成具体影响。
- 不为了完整感机械凑三点、三步或三类。有几项写几项。
- 优先正面说明职责和边界。只有纠正真实误解时才使用“不是……而是……”或“不仅……还……”。
- 让句子长短随信息变化。关键结论可以短，原因和取舍可以稍长，不把连续段落写成同一种句式。
- 一个事实只在最合适的位置完整说明一次；其他位置引用或简述，不换词重复。
- 有来源时写明来源。证据不足时标为待确认、假设或推断，不用模糊主体把判断伪装成共识。
- 沿用项目已经定义的术语。不要为了显得专业频繁替换同一个概念的名称。

## 文档

- 标题说明本节内容，不使用“赋能未来”“全面升级”等宣传口号。
- 每个段落解决一个问题。段落不能说明新事实、原因、取舍或动作时，考虑删除。
- 列表适合并列项、步骤和检查项；连续叙述优先用自然段，不把每句话都改成“短标签：说明”。
- 粗体只用于需要快速定位的结论、风险等级或决策项，不用粗体制造虚假的重点层级。
- 模板中的固定章节和字段必须保留；可选章节没有内容时省略，不用同义句填满。
- 结尾落到明确结论、负责人、确认项或下一步，不写只负责收束情绪的漂亮话。

改写示例：

```text
修改前：本能力旨在全面提升任务处理效率，为用户带来更加智能、高效的使用体验。
修改后：失败任务会保留原参数，用户可以在详情页直接重试，不需要重新创建任务。
```

```text
修改前：值得注意的是，权限配置在整个流程中起到了至关重要的作用。
修改后：没有 `approve` 权限的成员只能查看审批记录，不能提交或撤回审批。
```

## 代码注释

- 注释解释为什么这样实现、受什么约束、哪里容易误改，以及什么条件出现时需要升级。
- 不复述变量名、分支条件、循环或函数调用已经表达清楚的内容。
- 把注释放在它约束的代码旁边，尽量用一两句话说清楚。
- 不记录可以从版本历史获得的修改过程，例如“这里曾经改成……”。需要长期保留的是当前原因和约束。
- `TODO`、`FIXME` 或刻意简化注释必须写清触发条件或缺失能力，避免只写“以后优化”。
- 公共 API 注释说明调用合同、边界、错误和副作用；内部实现注释只补代码无法表达的信息。

注释示例：

```text
删除：// 遍历所有用户
保留：// 保持输入顺序；下游签名计算依赖稳定的用户排列。
```

```text
避免：// 临时方案，以后优化
改为：// 当前按单租户缓存；当同一进程承载多个租户时，缓存键必须加入 tenant_id。
```

## 写完后的快速检查

- 开头是否可以直接进入事实或结论。
- 是否有删掉后不影响含义的口号、过渡或总结。
- 是否连续使用相同句式、固定三段式或过多粗体标签。
- 每个判断是否有事实、来源或明确的不确定性标记。
- 文档是否重复，注释是否只是在复述代码。
- 改写是否意外改变了字段、状态、数字、验收或安全边界。
