# 团队写作风格

这份指南约束项目中的中文文档、用户可见说明和代码注释。目标是让内容准确、直接、像熟悉业务和代码的人写成，同时保留不同文档类型应有的结构。

## 约束优先级

先满足产物格式、机器状态、安全、证据和验收合同，再处理文风。发生冲突时，按以下顺序判断：

1. 产物的格式、状态、安全和证据合同。
2. 用户本轮明确提出的要求。
3. 当前技能针对 PRD、README、评审材料或代码注释的补充规则。
4. 本指南。
5. 目标文件相邻内容的既有写法。

风格调整不能改变事实、数字、状态值、字段名、验收标准和引用含义。

## 通用表达

- 先写结论、事实或变化，再补原因和背景。
- 写清楚主体、动作、对象和结果。能写“审批失败后保留已填写内容，并提供重试入口”，就不要写“全面提升流程体验”。
- 删除不承载信息的开场、过渡和总结，例如“下面我们来看”“值得注意的是”“综上所述”。
- 少用只表达态度的词。出现“重要”“高效”“智能”“全面”“显著”“赋能”时，检查它是否带来可验证信息；没有就删除或改写成具体影响。
- 不为了完整感机械凑三点、三步或三类。有几项写几项。
- 优先正面说明职责和边界。只有纠正真实误解时才使用“不是……而是……”或“不仅……还……”。
- 让句子长短随信息变化。关键结论可以短，原因和取舍可以稍长，不把连续段落写成同一种句式。
- 一个事实只在最合适的位置完整说明一次；其他位置引用或简述，不换词重复。
- 有来源时写明来源。证据不足时标为待确认、假设或推断，不用模糊主体把判断伪装成共识。
- 沿用项目已经定义的术语。不要为了显得专业频繁替换同一个概念的名称。

## 文档

- 标题说明本节内容，不使用“赋能未来”“全面升级”等宣传口号。
- 每个段落解决一个问题。段落不能说明新事实、原因、取舍或动作时，考虑删除。
- 列表适合并列项、步骤和检查项；连续叙述优先用自然段，不把每句话都改成“短标签：说明”。
- 粗体只用于需要快速定位的结论、风险等级或决策项，不用粗体制造虚假的重点层级。
- 模板中的固定章节和字段必须保留；可选章节没有内容时省略，不用同义句填满。
- 结尾落到明确结论、负责人、确认项或下一步，不写只负责收束情绪的漂亮话。
- 只保留当前结论、必要决策依据、开放问题和验证证据，不记录讨论过程、逐轮问答、AI 推演或纠正经过。修订时更新正文，不追加会话 Change Log；正式发布记录和必要验证证据仍按产物合同保留。

改写示例：

```text
修改前：本能力旨在全面提升任务处理效率，为用户带来更加智能、高效的使用体验。
修改后：失败任务会保留原参数，用户可以在详情页直接重试，不需要重新创建任务。
```

```text
修改前：值得注意的是，权限配置在整个流程中起到了至关重要的作用。
修改后：没有 `approve` 权限的成员只能查看审批记录，不能提交或撤回审批。
```

## 用户交互与 Emoji

Emoji 只作为帮助扫描和判断的功能性标记，不作为装饰。

- 允许用于对话中的选项菜单、进度更新、执行结果、风险提示和人工介入提示。
- Spec、PRD、Task、设计文档、Issue、PR、MR 等需要持久保存的正式产物默认不使用。
- 代码、代码注释、命令、日志、机器状态、固定字段和路径不使用。
- 每个选项或状态最多使用一个 Emoji；不要在标题和段落中连续堆叠。
- Emoji 后必须保留完整文字，不能让颜色或图形成为唯一语义来源。
- 只使用以下固定语义；没有匹配语义时直接使用文字，不临时引入装饰性图标。

```text
✅ 接受、成功、已完成
🔄 调整、重试、重新执行
⚠️ 风险、注意、需要检查
⛔ 阻塞、取消、停止
🧪 测试、验证
👤 需要用户输入或决策
↩️ 返回上一级
```

交互示例：

```text
1. ✅ 接受当前方案并继续
2. 🔄 调整当前方案
3. 👤 补充一个必要决策
4. ⛔ 取消，不执行写入
```

## 代码注释

- 不写代码注释，包括解释性注释、TODO/FIXME 和用作说明的 docstring。通过清晰命名、职责拆分、类型与可执行检查表达意图。
- 必须保留的许可证声明和编译器、检查器等工具指令不属于解释性注释；不要删除这些内容，也不要批量清除无关的既有注释。
- 必要的公共合同和决策依据写入相应正式文档，只写当前结论；可自动判断的约束落实为 lint、静态检查或 E2E 回归，不用注释掩盖代码坏味道。

改写示例：

```text
发现：用“保持输入顺序”的注释解释含糊实现。
处理：使用表达顺序语义的命名，并从公共入口验证输出顺序。
```

## 纠正落实

每次用户纠正 AI，都把适用规则落实为现有 lint、结构检查或 E2E 回归，并验证违规样例失败、合法样例通过。规则只覆盖已确认范围，不把单篇文档的偏好扩大到全项目；不能可靠自动判断时，说明缺口并向人类确认可执行判据。只读或仅允许修改文档时，交给有代码写权限的后续步骤落地，不能把文字约定当作检查已完成。文档只保存规则与证据，不保存纠正过程。

## 写完后的快速检查

- 开头是否可以直接进入事实或结论。
- 是否有删掉后不影响含义的口号、过渡或总结。
- 是否连续使用相同句式、固定三段式或过多粗体标签。
- 每个判断是否有事实、来源或明确的不确定性标记。
- 文档是否重复、含讨论过程，是否新增了解释性代码注释。
- 用户纠正是否对应已执行的自动检查，检查的适用范围与限制是否清楚。
- 改写是否意外改变了字段、状态、数字、验收或安全边界。
- Emoji 是否只出现在交互层，且每个图标都有完整文字说明。
